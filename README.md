# Старвуд-М — інтернет-магазин дитячих іграшок

Магазин іграшок від народження до 7 років: каталог із фільтром за віком дитини, знижки за
кількість, акції та промокоди, відгуки з модерацією, оформлення з Новою Поштою, самовивозом
чи «узгодимо», редагований контент, PWA-адмінка з мобільного, сповіщення Telegram / Email /
Web Push, автоматичне SEO (sitemap, JSON-LD, OG-теги). Товари, ціни й відгуки перенесені з
starvud.prom.ua (`php bin/cli.php import:prom`).

Чистий PHP 8.1+ без залежностей — працює на XAMPP і на shared-хостингу простим копіюванням.

**Запуск на бойовому сервері — покроково в [`DEPLOY.md`](DEPLOY.md).** Нижче — локальна
розробка й технічний довідник модулів (частина розділів описує можливості, які в Старвуді
вимкнені: торг, курси, дипломи, каса «Вчасно»).

## Запуск на ПК (XAMPP + Docker)

1. **Запустіть XAMPP** (Apache).
2. **Запустіть базу** — у папці `C:\xampp\htdocs\starvud` виконайте в командному рядку:
   ```
   docker compose up -d
   ```
   Перший запуск завантажить MySQL (~1 хв). База слухає порт **3308**, дані зберігаються у Docker-томі.
3. Відкрийте **https://localhost/starvud/** — при першому відкритті сайт сам створить таблиці й
   заповнить їх товарами з `database/prom` (фото — з `storage/import`).

**Перший вхід локально:** кнопка «Увійти» → «Увійти за поштою». Пошти на XAMPP немає, тому
код у режимі розробки дублюється в `storage/logs/php-error.log` — візьміть його звідти.
Права адміністратора собі видайте командою `php bin/cli.php grant-admin ваша@пошта`.

> Права читаються **лише** з таблиці `user_roles`; стовпець `users.role` лишився для показу
> й для міграції старих баз. Перенос `users.role → user_roles` живе в міграції 11, а вона
> відпрацьовує **до** сідера, на порожній таблиці користувачів — тому на свіжій базі
> демо-адмін і демо-продавець виходили взагалі без прав: адмінка не відкривалась, каса не
> вмикалась, і виглядало це як зламаний вхід. Тепер ролі створює сам `Seeder`, разом із
> користувачами. Заводячи персонал руками, памʼятайте те саме: роль — це рядок у
> `user_roles`, а не значення в `users.role`.

phpMyAdmin для бази: **http://localhost:8082** (лише з цього комп’ютера; користувач starvud, пароль — DB_PASSWORD з вашого `.env`).

## Структура

```
index.php          — точка входу (весь трафік через неї)
config.php         — конфігурація за замовчуванням (не редагувати)
config.local.php   — ваші локальні перевизначення (створіть за потреби)
app/Core           — ядро: роутер, БД, шаблони, авторизація, сповіщення, WebPush
app/Core/JsonLd.php — розмітка для пошуковиків (див. «Розмітка для пошуковиків»)
app/Core/Acquiring.php — оплата карткою через шлюз банку (див. «Оплата карткою»)
app/Controllers    — логіка сторінок (вітрина + адмінка)
app/Views          — шаблони
assets/            — стилі, шрифти, зображення, завантажені фото (uploads/)
bin/cli.php        — консольні команди: migrate | seed | fresh
storage/           — логи, сесії (не публікується)
storage/keys/      — ключі платіжного шлюзу (у .gitignore, назовні не віддається)
```

## Замовлення з кількох магазинів

Одне замовлення покупця автоматично розкладається на **підзамовлення** — по одному на магазин,
який реально виконує позиції. Так один продавець не бачить чужої роботи, а покупець має одне
замовлення з одним номером.

```
BOFU-260801-A3F2       головне: контакти, доставка, промокод, сума, зведений статус
├── BOFU-260801-A3F2/1  Магазин №1 — свої позиції, свій статус, свій продавець
└── BOFU-260801-A3F2/2  Магазин №2 — …
```

- **Хто виконує позицію** визначається при оформленні: самовивіз — обраний магазин; інакше той,
  де вистачає залишку на всю кількість (далі — де хоч щось є, і як запасний — магазин за
  замовчуванням, для товарів «під замовлення»). Залишки списуються саме з нього.
- **Підзамовлення створюється завжди**, навіть коли магазин один. Тоді передача позиції іншому
  магазину нічого не перебудовує, а доступи, сповіщення й статуси працюють одним шляхом.
- **Статус головного рахується сам**: він дорівнює найменш просунутій частині. Щойно всі магазини
  поставили «Доставлено» — головне стає «Доставлено» без ручних дій. Усі скасовані → скасовано.
  Адмін може проставити статус усім частинам одразу з картки головного замовлення.
- **Передача позиції в інший магазин** (адмінка → Замовлення → кнопка «→» біля позиції): позиція
  переїжджає в підзамовлення того магазину (створюється, якщо його ще не було), залишок повертається
  старому магазину й списується в нового, новий продавець отримує сповіщення. **Ціна не змінюється** —
  покупець платить рівно те, що бачив у кошику. Підзамовлення, що лишилось без позицій, закривається.
- **Скасування повертає товар на склад** — рівно те, що з точки колись зняли (позицію могли
  замовити понад залишок, і повертати «всю кількість» означало б подарувати магазину неіснуючий
  товар). Якщо на цей товар хтось чекав — йому одразу йде «зʼявився в наявності». Зняття
  скасування забирає товар назад і чесно пише в історію, якщо його вже розібрали.
- **Продавець** бачить у списку лише свої частини, але може відкрити замовлення цілком: контакти,
  доставку й те, які магазини ведуть решту частин (без права їх змінювати).
- **Покупець теж отримує сповіщення** (подія «Покупцю: рух його замовлення»): при оформленні й на
  кожній зміні статусу. Коли рухається одна частина розділеного замовлення — у повідомленні названо
  магазин і перелічено саме його товари, щоб «В дорозі» не читалось як «усе замовлення виїхало».
  Зареєстрованому — тими каналами, які він лишив собі в кабінеті, гостю — на пошту із замовлення.
- **Магазин за замовчуванням** (Налаштування → Замовлення) — точка, якій дістаються позиції, яких
  немає ніде. Без вибору їх забирає перша активна точка, і це залежить від порядку сортування
  магазинів, тож краще вказати явно.
- Уся історія — розділення, зміни статусів, передачі — пишеться в `order_events` і показується
  на сторінці замовлення.

Технічно: обидва рівні лежать в одній таблиці `orders` (`parent_id` = головне, `seq` = номер частини),
позиції `order_items` — **тільки** в підзамовленнях. Логіка зібрана в `app/Core/OrderFlow.php`.

## Каса: продаж за покупця (адмінка → Каса)

Продавець набирає замовлення сам: покупець подзвонив або прийшов у точку. Сторінка
`/admin/orders/new`, право `orders.create` (у ролі «Продавець» є за замовчуванням).
Замовлення виходить звичайним: той самий номер, підзамовлення магазину, списання залишків,
історія й сповіщення. У рядку лишається `source` (`site` | `phone` | `offline`) і
`created_by_user_id` — хто саме його завів.

**Три кроки: покупець → товари → отримання.** Продаж — послідовна розмова («хто ви» →
«що берете» → «як віддаємо»), і екран іде тим самим порядком. Спершу все було на одному
екрані, і воно там уміщалось, але дивитись доводилось усюди одразу: телефон покупця, плитка,
доставка й кнопка оформлення в різних кутах.

Кроки перемикаються **в браузері**, а не запитами: чек живе в сесії, і бігати за ним на
сервер щоразу, коли натиснули «Далі», нема потреби. Форма лишається **одна на всі три
кроки** — оформлення відправляє все разом, тож поля попередніх кроків нікуди не діваються.

Над кроками — стрічка з підсумками: кого записали, скільки позицій і на яку суму, як
віддаємо. Повертатись, щоб пригадати, не треба; клацнути можна на будь-який крок.
Єдина заборона — перейти до отримання з порожнім чеком: оформити його все одно не вийде,
і дізнатись про це краще одразу, а не після заповнення доставки.

Крок памʼятається при перезавантаженні. Їх за продаж два: зміна точки (у неї свій цінник,
тож плитка й чек перераховуються) і повернення з помилкою оформлення — воно завжди веде на
третій крок, бо саме там кнопка, з якої помилку отримали.

Швидкість набору не постраждала: сканер, пошук і плитка живуть на другому кроці разом.
Три способи покласти позицію, усі три працюють одночасно:

- **плитка товарів** — тап = +1. На кількох десятках позицій це швидше за будь-який пошук,
  і саме так влаштовані каси в невеликих магазинах;
- **сканер** — поле вгорі. Сканер працює як клавіатура: набирає код і тисне Enter, тож
  окремого «драйвера» не треба. Тримайте курсор у полі — і більше нічого робити не треба;
- **вітрина** — кнопка «Вийти на сайт». Унизу зʼявляється смужка продажу, і кнопки «У кошик»
  на сайті додають товар у цей самий чек. Це для випадку, коли покупцеві треба показати
  картку товару з фото й описом.

Чеком служить **звичайний кошик сайту** — той самий, у який кладуть покупці. Так працює все,
що вже написано: ліміти залишку, варіанти, ціни магазину, кнопки «У кошик». Власний кошик
продавця відкладається на час продажу й повертається, коли чек оформлено або скасовано:
чужа покупка не стирає те, що людина відклала собі. Живе чек у сесії — один продавець веде
один чек за раз (відкладені чеки — це вже чернетки в базі, і робити їх варто тоді, коли
зʼявиться жива черга).

**Покупець — поле чека, а не вхідні двері.** Номер вписують будь-коли: на початку, посеред
набору чи перед самим оформленням. Кнопка «Знайти» показує, кого знайшли і скільки в нього
замовлень, — продавець має бачити, що причепив саме ту людину.

**Чий це покупець — вирішує номер телефону** (`app/Core/Customers.php`):

- **номер є, акаунт знайдено** — замовлення лягає в історію цієї людини;
- **номер є, акаунта немає** — акаунт створюється (роль «покупець», службова пошта
  `…@offline.local`). Далі людина входить на сайт цим самим номером і бачить свою покупку;
- **номера немає** — замовлення анонімне (`user_id` порожній, `phone` — порожній рядок).

Номер склеює записи так само, як при вході через месенджер: він єдине стале імʼя покупця,
за ним же рахуються ліміти промокодів. Тому окремого «гостьового» акаунта тут немає —
він розірвав би історію покупок навпіл.

**Анонімно можна лише те, що анонімним і буває**: видача з рук у точці. Дзвінок без номера
не приймається (нічим підтвердити замовлення й нікому передзвонити), доставка — теж
(посилку нікому вручити). Це єдине обмеження форми; решта полів необовʼязкові.

Галка «Товар віддано покупцю» закриває замовлення тим самим рухом: статус одразу
«Доставлено», а сповіщення «нове замовлення» магазину не йде — його щойно зробив той,
хто його й виконав. Знята галка лишає замовлення в роботі (відклали до завтра).

Вона ж вирішує, чи пробивати **фіскальний чек**: коли налаштована каса, на третьому
кроці зʼявляється «Чим розрахувались» (готівка / картка) і поле «Отримано готівкою» з підрахунком
решти, а чек іде в ДПС разом з оформленням. Докладно — у розділі «Фіскальні чеки» нижче.

Ціни беруться за магазином-продавцем, разом із його акціями; зміна магазину перемальовує
і плитку, і чек — другої, javascript-ної копії ціноутворення навмисно немає. Промокод
перевіряється тими самими правилами, що й у кошику.

## Торг: «запропонуйте свою ціну»

Усі інші знижки призначає магазин: акція каже, що ми зараз продаємо дешевше,
промокод — хто має на це право, опт — скільки взяли, набір — що взяли разом.
Питання покупця «а за стільки віддасте?» досі не мало де прозвучати: його
ставили в дірект, продавець рахував у голові, ціну правили руками в замовленні,
а через місяць ніхто не міг пояснити, чому саме цей мед пішов по 480.

Тепер ця розмова записується.

### Як це виглядає

На сторінці товару, одразу під оптовою шкалою, стоїть блок **«Не влаштовує
ціна? Запропонуйте свою»**: кількість, ціна (за штуку або, якщо покупцю так
зручніше, за всю партію) і кілька слів від себе. Далі:

| Хід | Хто | Що відбувається |
|---|---|---|
| 1 | Покупець | Називає кількість і ціну. Пропозиція лягає в чергу продавця, покупцю приходить підтвердження |
| 2 | Продавець | **Погоджується**, дає **зустрічні умови** (свою кількість і свою ціну) або **відмовляє** |
| 3 | Покупець | На зустрічні умови — погоджується, пише свої або закриває розмову |
| … | | Коло повторюється, доки хтось не погодиться. Ходів не більше шести |

Домовились — ціна закріплюється за цією людиною на 48 годин (налаштовується).
Вона кладе позицію в кошик кнопкою «До кошика за домовленою ціною» й оформлює
замовлення сама: правити суму руками більше не потрібно.

### Що бачить продавець

Розділ **Продажі → Торг** в адмінці. Одна розмова — одна картка, і в ній чотири
числа, які важать лише разом:

- **Пропозиція** — скільки штук, по скільки, і що це за партію;
- **На сайті** — поточна вітринна ціна й на скільки відсотків нижче просять;
- **Опт на N шт** — скільки покупець отримав би **сам**, без розмови, за
  оптовою шкалою. Найважливіше число на екрані: якщо запитувана ціна вища за
  оптову, людина просто не знайшла шкалу, і «погоджуюсь» тут означає продати
  дорожче за власний прайс;
- **На складі** — чи вистачає на партію.

Поруч — хто просить: імʼя, телефон, скільки в цієї людини вже було замовлень і
на яку суму. Постійний покупець і людина з вулиці — різні розмови.

Число біля пункту меню показує, скільки розмов чекають відповіді. Пропозиція,
помічена через тиждень, дорівнює відмові: покупець на той час уже купив деінде.

### Межі, які роблять із торгу торг

- **Підлога.** Ціна, нижча за 50% вітринної (налаштовується), до продавця не
  доходить узагалі. Це не «наша мінімальна ціна», а фільтр від «мед за 10 грн»:
  десяток таких у черзі ховає одинадцяту, справжню. **Число покупцю не
  показується** — ні у формі, ні у відмові: назви ми його, і кожна наступна
  пропозиція була б рівно ним.
- **Ціна не нижча за вітринну** не приймається: це не торг, а описка, і
  заробляти на ній не варто.
- **Строк.** Погоджена ціна живе 48 годин, розмова без відповіді — 14 днів.
  Домовленість — не нова ціна товару назавжди: вона про цю кількість, цю людину
  й сьогоднішній день.
- **Шість ходів.** Далі лишається погодитись або відмовитись: коло, яке не
  закривається, — це не переговори.
- **Одна розмова на позицію.** Людина, якій відповіли «ні», не заводить нову
  гілку з тією ж ціною.
- **Двадцять ходів на добу** з одного джерела (RateLimit).

### Домовлена ціна не складається ні з чим

Ні акція, ні опт, ні набір, ні промокод на таку позицію більше не діють.
Не через жадібність: продавець назвав кінцеве число, дивлячись на кількість і
на цю людину. Відняти від нього ще десять відсотків означало б, що названа
ціна нічого не означала.

Наслідки, які видно в кошику:

- домовлений рядок стоїть **окремо** від звичайного рядка того самого товару —
  десять банок за домовленою ціною і ще дві за звичайною цілком законні;
- кількість домовленої партії **не правиться кнопками**: ціну назвали саме за
  цю партію. Прибрати рядок можна завжди;
- домовлені штуки **не рахуються** в оптовий поріг сусіднього рядка — інакше
  одна знижка тихо купувала б другу;
- у кошику й на оформленні рядок підписаний «домовлена ціна», а в історії
  замовлення зʼявляється запис із умовами й прайсовою ціною. Без цього сума не
  сходиться ні з прайсом, ні з жодною знижкою, і пояснити її нічим.

Кошик перевіряє домовленість **на кожному запиті**, а не при додаванні: сесія
переживає і скасування угоди, і кінець строку, і зняття товару з продажу. Рядок,
який більше не можна підтвердити, зникає — але з поясненням, а не мовчки.

### Мовчанка — головний ворог торгу

Найгірший сценарій тут не «незручно відповідати», а те, що не відповів ніхто:
покупець назвав ціну, продавець не зайшов в адмінку, за два тижні розмова тихо
згасла. Людина не отримала нічого — тобто ми запросили до розмови й не прийшли.
Одна відсутня функція коштує магазину менше, ніж один такий випадок.

Тому три речі працюють проти мовчанки:

**Обіцянка вголос.** У формі написано, коли ми відповімо — «продавець
відповість **протягом доби**». Число береться з налаштування
`offers_reply_hours`, і воно ж будить нагадування: обіцянка й будильник — одне
значення, інакше одне з них рано чи пізно почне брехати.

**Глибокі посилання.** Сповіщення веде не в розділ, а одразу на потрібну
розмову — `…/admin/offers?tab=todo#o57` продавцю, `…/bargain#o57` покупцю.
Вкладка добирається за станом розмови, картка підсвічується на пару секунд.
Читають ці листи з телефона, і пошук потрібного рядка серед десятка інших — це
і є та незручність, через яку відповідь відкладають «до компʼютера», а звідти
на завтра.

**Нагадування за розкладом.** Команда проходить чотири мовчанки:

```bash
php bin/cli.php offers:remind
```

| Мовчанка | Кому пишемо |
|---|---|
| Пропозиція чекає на нас довше за обіцяний строк | Продавцю |
| Наші зустрічні умови так само довго чекають на покупця | Покупцю |
| Погодженій ціні лишились години (чверть строку) | Покупцю |
| Розмова вже закрилась сама | Покупцю |

Кожне повідомлення одноразове — мітки `reminded_at` і `notified_at` у самому
рядку. Перша обнуляється будь-яким ходом (після відповіді відлік починається
заново), друга не обнуляється ніколи: закриття буває один раз. Розмова, яка
нагадує про себе щогодини, — це не турбота, а спам, після якого людина вимикає
канал цілком.

Два кінці розрізняються навмисно: **«Ми не встигли відповісти»** (`expired`) і
**«Строк домовленої ціни вийшов»** (`lapsed`). Для покупця це протилежні
новини, і ховати першу за словом «протерміновано» було б нечесно — не відповіли
саме ми.

У cron раз на годину. Обіцянка міряється добою, тож частіше немає сенсу, а
рідше — прострочить попередження про кінець строку:

```
20 * * * * php /home/USER/site/bin/cli.php offers:remind
```

Хвилина не нульова з тієї ж причини, що й у `yt:refresh`: о рівній годині на
shared-хостингу стартують крони всіх сусідів одночасно.

### Налаштування

**Налаштування → Торг**: головний вимикач, підлога у відсотках, обіцяний строк
відповіді, строк дії погодженої ціни. Окремі товари виводяться з торгу галкою в їхній картці
(«Торг → Дозволити торг за цей товар») — так само, як вимикається опт. Товар без
ціни («за запитом») з торгу випадає сам.

Право `offers.manage` («Торг: розглядати пропозиції ціни від покупців») є в
продавця й адміністратора. Події сповіщень — `offer_new` (персоналу) та
`offer_reply` (покупцю).

Адреси навмисно не `/offer*`: цей шлях зайнятий публічною офертою. Покупець
працює з торгом на `/bargain`, продавець — на `/admin/offers`.

## Розділи й підрозділи каталогу

Розділ каталогу може містити підрозділи — рівно на один крок углиб:

```
Мед і смаколики          ← розділ верхнього рівня, стоїть у панелі
├── Квітковий мед         ← підрозділ, схований за стрілкою
└── Подарункові набори
```

У панелі каталогу розділ із підрозділами має **стрілку**. Вона нічого не завантажує —
розгортає ряд підрозділів на місці, і покупець переходить одразу в потрібний, минаючи
сотню позицій усього розділу. До цього вибір був такий: або відкрити «Мед» цілком, або
не відкривати; десяток розділів і всі їхні сорти одним рядом зайняли б пів екрана.

Правила, які з цього випливають і зафіксовані в `tests/categories.php`:

- **Розділ показує всю свою гілку.** Товар лежить рівно в одній категорії, тож щойно
  власник розклав мед по сортах, «Мед» без цього правила став би порожньою полицею.
  Гілку (`Catalog::branchIds`) питають усі, хто відбирає товари категорією: каталог,
  панель фільтрів, акція на категорію, плитка каси, фільтри в адмінці.
- **Глибина одна.** Підрозділ не може мати власних підрозділів, а розділ із підрозділами
  не можна вкласти в чужий. Тримає це адмінка, а не база: другий крок углиб вимагав би
  крихт у самій панелі, а підрозділи підрозділів дрібнішають до порожніх полиць.
- **Вимкнений розділ не ховає своїх підрозділів** — вони піднімаються у верхній ряд.
  Інакше одна знята галка тихо прибирала б із сайту півкаталогу.
- **Видаляється розділ разом із підрозділами.** Галка на розділі ставить галки і їм,
  а попередження перед збереженням називає поіменно все, що зникне.

Заводять підрозділи в **адмінці → Категорії**, полем «Всередині розділу» — і в формі
додавання, і в таблиці. Тип підрозділ успадковує від розділу: «Відео» всередині «Товарів»
означало б, що розділ показує те, чим не є.

Без JS стрілка не працює — тому підрозділи досяжні й так: розділ відкривається звичайним
посиланням, а на його сторінці ряд підрозділів уже розгорнутий. Пошуковик із тієї ж
причини бачить посилання на всі підрозділи (вони в розмітці, лише сховані), а крихти
підрозділу ведуть через його розділ.

На **касі** підрозділи стоять одним рядом із розділами, без стрілки: там усе рахується на
один тап, і зайвий крок «розгорнути» коштував би дорожче за довший ряд, який і так
прокручується вбік.

### Категорії в шапці сайту

Панель у каталозі допомагає тому, хто вже в магазині. Щоб потрапити в потрібний розділ
**із будь-якої сторінки**, поруч із пунктом «Магазин» у шапці стоїть стрілка — вона
відкриває список розділів із вкладеними підрозділами, і клік веде на `/shop?cat=…`,
тобто в каталог з уже обраною категорією.

- **Стрілка окремо від назви.** «Магазин» лишається звичайним посиланням у каталог:
  пункт меню, який замість переходу розкриває список, перестає вести туди, куди обіцяє.
- **Кліком, а не наведенням.** На телефоні наведення немає, і меню, яке відкривається
  по-різному на різних пристроях, довелося б тримати узгодженим двома способами замість
  одного. Закривається кліком повз меню або `Esc`.
- **У мобільному меню** те саме, але згорнуте: сім пунктів сайту й розгорнутий список
  категорій не вміщаються в екран разом.

Категорії шапка питає сама (`Catalog::categoryTree()` у `partials/header.php`) — так само,
як підвал питає контакти. Носити цей список через кожен контролер означало б пам'ятати
про нього в кожному новому.

## Коди й штрихкоди (адмінка → Каталог)

Два різні поля, і це не дублювання:

- **артикул** (`sku`) — ваш внутрішній код для обліку, придумуєте ви: «MED-LIP-05»;
- **штрихкод** (`barcode`) — те, що надруковано на етикетці й читає сканер: EAN-13.

В одному полі вони рано чи пізно перетруть одне одного, тому їх два. У товару з фасовками
коди належать **фасовці**: етикетку клеять на банку, а не на «мед узагалі», і скан має
потрапити в конкретну позицію.

Заповнюють їх на окремому екрані **Каталог → Коди й штрихкоди**. Він заточений під одну роботу:
пройтись товарами з річчю в руках і проставити коди, тож угорі **фільтр** — пошук (назва,
артикул, код), категорія й готові добірки:

| Добірка | Навіщо |
|---|---|
| **Без штрихкоду** | кому ще не проставлено — головна добірка, з нею й ходять |
| **Зі штрихкодом** | перевірити вже зроблене |
| **З помилкою** | збита контрольна цифра або однаковий код у двох позицій |
| **Свої коди** | ті, що створені тут, — їх треба надрукувати й наклеїти |

Три способи заповнити, бо в житті трапляються всі три:

- **фабрична етикетка є** — USB-сканер (станьте в поле й піднесіть) або **📷** просто в рядку:
  камера читає код і кладе його в це поле;
- **етикетки немає** (своя банка меду) — **✨** у рядку: створює власний код **для цієї однієї
  позиції**. Масової кнопки «заповнити все» немає навмисно: коди проставляють по одному, разом
  із наклеюванням, і «створити 200 кодів одним кліком» лише плодить те, чого ніхто не надрукує;
- **код відомий із накладної** — ввести руками.

**Свої коди впізнаються з першого погляду**: вони починаються з `200` і позначені міткою
«свій код». Діапазон 20–29 стандарт GS1 лишив магазинам для внутрішнього вжитку, тож такий код
гарантовано не збігається з жодним чужим товаром у світі. Код виводиться з номера позиції
(`Barcode::make`), тому повторне натискання дає той самий код, а не новий.

**🖨 у рядку** відкриває наліпки на друк — 6/12/24/48 копій на аркуші, з назвою позиції над
кожним кодом. Друкується збережений код: малюнок креслить сервер (`Barcode::svg()`), і другої
копії цього креслення в браузері немає навмисно.

**Описка ловиться одразу.** Остання цифра штрихкоду рахується з попередніх — саме щоб її було
видно. Код зі збитою цифрою підсвічується, поруч пишеться, яким він має бути, і є кнопка
«виправити». Так само підсвічуються однакові коди: інакше каса щоразу братиме той товар, який
трапиться першим, і продавець цього не помітить.

Код, записаний на **товарі з кількома фасовками**, не спрацює ніколи — сканер не знатиме, яку
фасовку класти в чек. Такий код показується з поясненням і кнопкою «перенести в першу фасовку».
Якщо ж фасовка одна, код товару працює: одна фасовка — це не вибір (так само поводиться й кошик
на вітрині).

Каса шукає в такому порядку: штрихкод фасовки → штрихкод товару → артикул фасовки → артикул
товару. Збіг **тільки точний**: «схожий» код означав би чужий товар у чеку. Поки жоден код не
заповнений, каса каже про це просто на екрані сканера — інакше сканер виглядав би зламаним.

### Чим сканувати

- **USB-сканер** — нічого налаштовувати не треба: для компʼютера він звичайна клавіатура.
  Тримайте курсор у полі сканера, підносьте до етикетки — позиція лягає в чек сама.
- **Камера** — кнопка «📷 Камера» на касі. На Android працює вбудований у браузер
  `BarcodeDetector`, а де його немає (на Windows — ніде) вмикається власний декодер
  `assets/js/barcode.js`: EAN-13 і EAN-8, кілька смуг кадру, обидва напрямки.
  Камеру браузер дає лише на `https://` (або `localhost`) — по локальній http-адресі
  з телефона вона не увімкнеться, і каса про це скаже.

Прочитаний код завжди перевіряється **контрольною цифрою**: вигаданий код у чеку гірший за
непрочитаний — чужий товар ляже туди тихо. Декодер живе в браузері, тож і перевіряється в
браузері: відкрийте `tests/barcode.html` (генерує штрихкоди, крутить їх, зашумлює й читає).

## Як людина стає покупцем

Три шляхи, і в них різна ціна входу:

| Шлях | Що потрібно | Що він доводить |
|---|---|---|
| **Пошта, код у листі** | будь-яка скринька — ukr.net, meta.ua, робоча | що скринька її |
| **Telegram** | акаунт у Telegram | що скринька не при чому, а **номер телефону її** |
| **Google** | акаунт Google | що скринька її |

Четвертого шляху — «увійти за номером телефону» — як реєстрації не існує, і це не забута
функція. Ані Telegram, ані Viber не дають боту написати першим за номером: бот відповідає
лише тому, хто написав йому сам. Тому код за номером доставляється тільки у **вже
підключений** месенджер, тобто це вхід, а не реєстрація. Реєстрація за номером зʼявиться
разом із SMS-шлюзом — і тоді ж номер почне доводитись без Telegram.

Купити можна взагалі без входу: гість оформлює замовлення й відкриває його за посиланням
із токеном. Акаунт потрібен по інше — історія замовлень, збережені адреси, «повідомити про
наявність», торг.

### Вхід поштою: одноразовий код

Вхід і реєстрація — одна дія: акаунт створює саме володіння скринькою, а воно доводиться
кодом. Через це форма й відповідає однаково на знайому та незнайому адресу — перебором
чужих адрес нічого не дізнатись.

- **Код, а не посилання з листа.** Лист іде звичайним `mail()`, і поки на домені немає SPF
  і DKIM, частина листів осідає в теці «Спам». Код цифрами звідти можна переписати руками —
  посилання ж поштові фільтри ще й переписують на свої «безпечні» адреси. Понад те, код
  нікуди не веде: людину не привчають відкривати посилання з листа «від магазину».
- **Код видно в темі листа** — щоб не відкривати сам лист, особливо коли він у спамі.
- **Одноразовий і на 15 хвилин.** Лист лишається в скриньці назавжди, а скриньку читають і
  зі старого телефона — тому код вмирає першим використанням, а не строком.
- **Стелі дві**: не більше 3 кодів на годину на адресу і 5 на годину з одного IP. Перша —
  щоб формою не залили чужу скриньку, друга — щоб сайт не став безкоштовною поштовою
  гарматою. Без першої зміна IP знімала б обмеження з конкретної жертви.
- **Технічні адреси не приймаються** (`@offline.local`, `@telegram.local`, `@viber.local`).
  Це не скриньки, а імена записів: покупця з `@offline.local` заводить продавець у точці, і
  такий запис має лишатись недосяжним для входу ззовні.
- **Пошта не доводить номер.** Вхід поштою ніколи не ставить `phone_verified_at` — див.
  наступний розділ.

Перед налаштуванням SPF/DKIM у HostIQ вхід поштою працює, але частина людей знайде лист
лише в спамі. Це найдешевше, що можна зробити для цього входу: два TXT-записи в DNS.

Лист із кодом іде з окремої адреси (`mail_from_auth`, типово `login@домен`), якщо її задано, —
щоб скарги на листи про акції не тягли за собою доставку того єдиного листа, без якого в
акаунт не увійти. Три поштові поля описані в розділі «Інтеграції».

### Підтверджений номер — і навіщо він

`users.phone_verified_at` відповідає на питання «чим доведено, що цей номер — його». Доводить
його сьогодні лише Telegram: у контакті є `contact.user_id`, який звіряється з `from.id`.
Вписаний у профілі номер не доводить нічого — вписати можна будь-який.

Різниця не косметична. Замовлення, які продавець оформлює по телефону, знаходять покупця саме
за номером (`Customers::resolve`), тож «номер у профілі = мій номер» означало б: знаєш номер
сусіда — бачиш його покупки, адресу й суми. Саме через цю дірку прибрано вхід через Viber
(66a8175), але через профіль вона лишалась відкритою для всіх, хто увійшов.

Тепер замовлення з каси причіпляється до акаунта у двох випадках (`Customers::ownsPhone`):

1. номер **підтверджений**;
2. це **запис, який завів продавець** — технічна адреса `@offline.local` і жодного каналу
   входу. У такий запис не може увійти ніхто, тож і привласнити його нема кому; він
   дістанеться тому, хто доведе номер, — вхід через Telegram склеює записи за номером.

В усіх інших випадках замовлення лишається анонімним, і каса каже це продавцю прямо
(стан «номер записаний у акаунті, де його не підтверджено»), а не мовчить.

**Зміна номера скидає підтвердження** — і в профілі, і в адмінці. Підтвердження належить
номеру, а не акаунту: інакше той, хто колись довів свій номер, вписавши чужий, отримав би
його вже «підтвердженим».

**Заднім числом нічого не підтверджено.** Міграція 49 не позначає доведеними навіть номери
з привʼязаним Telegram: звірка `contact.user_id` зʼявилась лише в 0722edf, а до неї переслати
чужий контакт було можна — тобто серед старих записів теоретично є рівно ті, заради яких усе
це й робиться. Втрати немає: бот просить контакт при кожному вході, тож номер стає доведеним
першим же входом, а **гостьові замовлення на цей номер у ту саму мить переїжджають у кабінет**
(`Customers::claimOrders` — лише анонімні; те, що вже комусь належить, не перечіпляється
ніколи).

## Вхід через месенджер

Вхід через Telegram / Viber завершується **лише після того, як людина поділиться номером
телефону** — кнопкою в самому боті (`request_contact` у Telegram, `share-phone` у Viber).
До цього моменту токен входу лишається непідтвердженим, а акаунт не створюється.

Контакт просимо **щоразу**, навіть коли номер в акаунті вже записаний: записаний номер
нічого не доводить, його міг вписати хто завгодно з клавіатури. Володіння підтверджує
лише контакт, надісланий самим месенджером. Один `chat_id` завжди належить одному акаунту —
коли номер приводить до іншого запису, стара прив'язка знімається.

Номер приводиться до єдиного вигляду однією функцією на весь сайт — `AuthTokens::normPhoneAny()`.
Український код країни має **сталу довжину**: `380` і рівно 9 цифр. Зайва цифра (`+38063463513278`)
відхиляється, а не проходить як «закордонний номер»: коду країни `380X` не існує ні в кого, тож це
завжди описка — і без цього правила замовлення поїхало б на номер, якого немає, а помітилось би це
аж при дзвінку. `AuthTokens::phoneProblem()` пояснює людині, що саме не так, замість одного
«неправильний номер» на всі випадки.

**Дублікати неможливі структурно**: на `users.phone` стоїть UNIQUE-індекс. Перевірки в коді
(`Profile`, `Users::readPhone`, `BotAuth`) лишаються — вони дають людині зрозуміле пояснення, —
але навіть новий шлях, який їх омине, не заведе другого акаунта на той самий номер. `NULL`
дозволений скільки завгодно: акаунт без номера просто не пройде далі профілю.

Причин дві. Телефон обовʼязковий (гейт у `App::run()` не пускає далі профілю), тож без нього
людина входила і одразу впиралась у форму. І головне: покупець, який колись замовляв за
номером, отримував **другий** акаунт — замовлення лишались у першому. Тепер номер склеює
записи: `BotAuth::resolveUser()` шукає спершу за телефоном і лише потім за id месенджера.

У Telegram обовʼязково звіряється `contact.user_id` з `from.id`: переслати чужий контакт із
адресної книги можна, і без цієї перевірки чужим номером можна було б увійти в чужий акаунт.
У Viber перевірка не потрібна — `share-phone` віддає номер самого співрозмовника.

Тексти всіх кроків бота редагує адмін (Налаштування → «Тексти бота при вході»), порожнє поле
повертає типовий. Після входу бот шле кнопку-посилання назад на сайт — адресу візьміть із поля
«Адреса сайту для кнопки в боті»: Viber стукає у webhook власним запитом, і визначити її з
контексту не завжди можливо.

## Налаштування інтеграцій (адмінка → Налаштування)

- **Google OAuth**: Google Cloud Console → Credentials → OAuth Client ID (Web).
  Redirect URI показано на сторінці налаштувань. Поки ключів немає, кнопки Google просто
  немає — вхід за поштою працює без жодних налаштувань.
- **Telegram**: створіть бота у @BotFather → вставте токен. Кожному продавцю/адміну впишіть
  його Chat ID (адмінка → Користувачі). Сповіщення про нові замовлення прийдуть у Telegram.
- **Нова Пошта**: API-ключ з кабінету novaposhta.ua → автопідказки міст і відділень у checkout
  і створення накладних просто із замовлення. Див. окремий розділ «Нова Пошта» нижче.
- **Оплата карткою (Raiffeisen Bank)**: інтернет-еквайринг — покупець платить при оформленні,
  а не при отриманні. Merchant ID, Terminal ID і ключі видає банк. Див. окремий розділ
  «Оплата карткою» нижче.
- **Фіскальні чеки (ПРРО)**: постачальник і маршрут до каси. Ключ підпису не обовʼязково
  віддавати в хмару — див. окремий розділ «Фіскальні чеки» нижче.
- **Google Maps**: ключ для карти точок продажу — див. окремий розділ «Карта точок продажу»
  нижче. Без ключа сайт працює як працював: замість карти адреса з кнопкою маршруту.
- **Web Push**: ключі генеруються автоматично; на телефоні запрацює після переносу на HTTPS.
  Якщо на Windows ключі не створюються — openssl не знаходить `openssl.cnf`; вкажіть його
  у змінній `OPENSSL_CONF` (`C:\xampp\apache\conf\openssl.cnf`).
- **Кнопка «Перевірити зʼєднання»** (там же, у Налаштуваннях) питає Telegram, Viber і Нову Пошту
  тим, що зараз у полях, **нічого не зберігаючи**. Виклики лише читальні: webhook не переставляє,
  листів і повідомлень не шле. Показує, зокрема, **куди вказує webhook Viber-бота** — у бота він
  лише один, тож якщо там чужа адреса, збереження токена забере бота з того сайту.
- **Розсилка** (адмінка → Розсилка): адреси збираються лише за явною галкою згоди — при оформленні
  замовлення або в профілі. Експорт CSV містить колонку `unsubscribe_url` — це персональне посилання
  на відписку, яке **обовʼязково** треба вставляти в кожен лист розсилки.
- **Пошта відправника** — три поля в Налаштуваннях, і заповнене обовʼязково лише перше:
  - `mail_from` — **`shop@ваш-домен`**: замовлення, статуси, сповіщення. Скринька має бути жива:
    покупці відповідають на такі листи, і в noreply@ ці відповіді зникають безслідно.
  - `mail_from_auth` — **`login@ваш-домен`**: тільки коди входу. Сенс розділення в тому, що
    репутація адреси спільна для всіх її листів: одна скарга «це спам» на лист про акцію
    просаджує доставку — і разом із нею перестають доходити коди, тобто люди не можуть увійти.
    Порожнє поле — коди підуть із `mail_from`, як раніше.
  - `mail_reply_to` — куди веде кнопка «Відповісти», якщо у From стоїть скринька, яку ніхто
    не читає. Порожнє — відповідь іде в `mail_from`.

  Домен у цих адресах має збігатися з доменом сайту. Власний gmail тут — найгірший вибір із
  можливих: `gmail.com` каже приймачам, що його листи йдуть лише з його серверів, наш хостинг
  ним не є, і лист відхиляють ще до теки «Спам». Кнопка «Перевірити зʼєднання» про це попереджає.
  Там же, у DNS хостингу, пропишіть **SPF, DKIM і DMARC**: без них частина людей не побачить
  коду входу взагалі. Незаповнені поля означають `shop@` і `login@` на домені сайту — тобто
  скриньки, яких може не існувати; листи підуть, але відповіді й звіти про недоставку зникнуть.
- **Демо-входу більше немає** (він давав адмін-права одним кліком без пароля). Права на
  локальній машині й на новому сервері видає `php bin/cli.php grant-admin ваша@пошта`.
  Якщо в `config.local.php` лишився рядок `demo_login` — його можна видалити, `prod-check`
  про це нагадає.

## Нова Пошта: накладні й відстеження

Замовлення проходить шлях від «покупець обрав відділення» до «посилку отримано» без жодного
переписування номерів руками: накладна створюється кнопкою в картці замовлення, а її статус
далі оновлюється сам і доходить до покупця в кабінет.

### Що налаштувати (один раз)

1. **API-ключ** — кабінет novaposhta.ua → Налаштування → Безпека. Вставити в адмінці →
   Налаштування → «Інтеграції та SEO». Ключ безкоштовний.
2. **Відправник** — там же, картка «Нова Пошта: відправник». Натисніть «Підтягнути з Нової
   Пошти»: контрагента й контактну особу беремо з вашого кабінету, вигадати їх не можна —
   накладна створюється саме від їхнього імені. Далі місто й відділення відправлення.
3. **Типова накладна** — вага, опис вантажу, хто платить за доставку, чи ставити післяплату
   за замовчуванням. Це лише передзаповнення форми: продавець може змінити будь-що перед
   створенням.
4. **Кнопка «Перевірити зʼєднання»** покаже окремим рядком «НП: відправник» — чи вистачає
   даних, щоб накладна взагалі створилась.

**Магазин може відправляти зі свого відділення** (Магазини → рядок точки → «Відправлення
Новою Поштою»). Порожньо — їде зі спільного. Контрагента там немає навмисно: він належить
кабінету НП, а кабінет (тобто ключ) у сайту один на всі точки.

**Вага береться з товарів** (Каталог → товар → «Вага, кг»; у товару з фасовками — у самій
фасовці). Форма накладної рахує вагу × кількість по всіх позиціях, а де ваги немає — бере
типову з налаштувань. За вагою НП рахує гроші, тож проставити її варто.

### Накладна на кожну частину замовлення

Розділене між магазинами замовлення дістає **стільки накладних, скільки магазинів його
виконують**. Це не ускладнення заради ускладнення: дві коробки з різних міст фізично не
можуть їхати під одним номером. Покупець бачить список номерів із назвою магазину біля
кожного, а продавець — лише свою частину.

Створення (адмінка → Замовлення → картка → блок під позиціями):

- **«Створити накладну»** — звичайний шлях. Вага, місця, оцінка, післяплата, платник —
  усе передзаповнене, лишається звірити. Після створення: частина переходить у «В дорозі»,
  покупцю йде номер із посиланням на відстеження.
- **«Вписати номер»** — для накладних, оформлених у кабінеті чи застосунку НП або просто на
  відділенні. Це не «запасний варіант на випадок поломки», а звичайний шлях: далі все працює
  однаково, трекінгу потрібен лише номер. Вписаний номер одразу перевіряється в НП.
- **«✕ Накладна»** — відкріпити. Скасувати накладну в НП вдається, лише поки посилку не
  прийняли у відділенні; якщо вже прийняли, номер відкріпиться тут, а посилка їхатиме далі —
  про це буде сказано прямо.

**Куди везти, береться із замовлення** — форма створення накладної адресу не питає: покупець
обрав її сам. Але саму доставку в картці змінити можна, і це окрема дія: блок «Доставка»
праворуч → «**Змінити доставку**». Там перемикається **спосіб** (Нова Пошта ↔ Самовивіз ↔
Інше) і все, що йому належить: відділення чи вулиця для пошти, точка видачі для самовивозу,
довільний опис для «іншого». Це для випадків, коли покупець передумав або домовились
телефоном, — інакше довелося б перестворювати замовлення, втрачаючи його номер і історію.

Три речі, які варто знати про цю форму:

- **зміна стосується всього замовлення** — усі магазини везуть в одне місце. Точка видачі
  при самовивозі ставиться головному замовленню й не чіпає того, який магазин що виконує;
- **покупцю повідомлення не йде**: він або сам попросив, або ви щойно з ним говорили;
- **поки виписана накладна, доставка не змінюється** — спершу відкріпіть її. Інакше посилка
  поїхала б туди, куди її вже відправили.

Окремий випадок — адреса, записана **текстом, без звʼязку з довідником** (старе замовлення
або людина вписала відділення руками, не торкнувшись підказки). Накладну за нею не створити:
НП приймає посилання, а «Відділення №5» у місті буває не одне. Тоді та сама форма відкрита
одразу й названа «⚠️ Уточнити відділення для накладної» — оберіть зі списку, покупцю робити
нічого не треба.

**Курʼєрська доставка** працює нарівні з відділенням: покупець обирає «Курʼєром на адресу»
в checkout, вулиця береться з довідника НП, і накладна створюється з тими самими кнопками.

### Відстеження

Статуси тягне команда, яку ставлять у cron **раз на годину**:

```
0 * * * * php /home/USER/site/bin/cli.php np:track
```

За прохід питає до 100 накладних (стільки НП приймає за запит), першими — ті, кого
перевіряли найдавніше. Отримані й видалені не питає ніколи: їхній стан уже не зміниться,
а ліміт запитів у НП спільний на весь сайт. У картці замовлення є кнопка **«↻ Статус»** —
для випадку «покупець дзвонить просто зараз і питає».

Що з цього виходить само:

- посилка поїхала або прибула у відділення → частина стає «В дорозі»;
- посилку отримано → частина стає «Доставлено», а коли всі частини закриті — і все замовлення;
- статус **не відкочується назад**: продавець міг поставити «Доставлено» руками (покупець
  забрав у точці), і скасовувати його рішення через те, що НП ще не оновилась, не можна.

**Покупцю пишемо тричі, не частіше**: коли є номер, коли посилка чекає у відділенні й коли її
отримано. «Виїхала з сортувального центру» він подивиться в застосунку НП, якщо схоче; від нас
це було б спамом. Подія називається «Покупцю: накладна й рух посилки» — її, як і решту, можна
вимкнути в Налаштуваннях сповіщень, а покупець вимикає собі сам у кабінеті.

**Де це видно.** Покупцю — у кабінеті (`/orders`): номер із кнопкою «Копіювати», статус,
орієнтовна дата, сума післяплати. Гостю — на сторінці підтвердження замовлення за тим самим
посиланням, що він отримав при оформленні: кабінету в нього немає, і це його єдине вікно.
Продавцю — у списку замовлень під статусом, плюс фільтр: **без накладної** (те, що треба
зібрати й відправити — головна добірка на початок дня), **у дорозі**, **чекає у відділенні**
(покупець не забирає — час подзвонити), **проблема**.

### Що саме отримує покупець

Два повідомлення з усіх, що є в системі, читає не персонал, а клієнт: «Покупцю: рух його
замовлення» і «Покупцю: накладна й рух посилки». Тон у них інший, ніж у решти, і це навмисно.
Усе інше — рядок у журналі для свого, ці два — лист від магазину людині, яка щойно лишила тут
гроші. Звідси цілі речення, звертання на «ви» й підпис магазину замість обриву на півслові.

```
Тема: Замовлення BOFU-260817-4C1A — прибуло у відділення

Ваше замовлення прибуло у відділення Нової Пошти.

Замовлення: BOFU-260817-4C1A
Експрес-накладна: 20450000000123
Орієнтовна дата доставки: 19.08.2026
До сплати при отриманні: 1 240 грн

Відстежити: https://novaposhta.ua/tracking/?cargo_number=20450000000123

Beekeeper of Ukraine
```

Три речі, які тут зроблені свідомо:

- **Тема листа називає подію.** Раніше всі листи із сайту приходили з темою
  «Beekeeper of Ukraine — сповіщення» — у скриньці з двадцятьма непрочитаними це рівно нуль
  інформації. Тема — єдине, що видно до відкриття (`Notify::SUBJECTS`).
- **Після отримання зникають рядки, які втратили сенс.** Ні дати доставки, ні «до сплати», ні
  «відстежити» людині, яка вже тримає посилку в руках. Кожен такий рядок несе власний підпис
  і порожніє цілком, а порожній рядок шаблон прибирає сам.
- **Одна подія — одне повідомлення.** Коли трекінг переводить замовлення в «Доставлено», зміна
  статусу більше не шле покупцю власного листа: він щойно отримав конкретніший, з номером
  накладної. Персоналу при цьому надходить усе як раніше — для нього це різні новини
  (`OrderFlow::setStatus($id, $status, $userId, tellCustomer: false)`).

Тексти лишаються редагованими в адмінці. Якщо у правилі збережено дослівно старий типовий
текст — його ніхто не чіпав, і показується новий; щойно адмін змінить бодай літеру, лишається
його варіант (`Notify::template()`). Міграції для цього не потрібно.

### Права

Створювати накладні дозволяє окреме право **«Створювати накладні Нової Пошти»** (`orders.ship`,
у ролі «Продавець» є за замовчуванням). Дивитись і вести замовлення можна й без нього: накладна
коштує грошей і створюється від імені магазину, тож це не додаток до «змінювати статус».
Продавець керує накладними **лише своїх** частин, адміністратор — усіма.

## Оплата карткою: інтернет-еквайринг Raiffeisen Bank

Покупець платить при оформленні, а не при отриманні. Для магазину це не «ще один спосіб
оплати», а інший порядок подій: гроші приходять **до** відправлення, і непроплачена посилка
більше не їде туди й назад за рахунок продавця.

Технічно це шлюз **UPC e-Commerce Connect** — процесинг групи Raiffeisen, який обслуговує
картковий трафік банку. У документації, яку дасть банк, він так і зветься; Merchant ID,
Terminal ID і доступ до тестового середовища видає при цьому **банк-еквайєр**, а не UPC.

Карткових даних сайт не бачить взагалі: покупець вводить їх на сторінці шлюзу. У коді немає
жодного поля картки, і не має зʼявитись — щойно номер картки торкнеться нашого сервера,
магазин потрапляє під PCI DSS цілком, а не під найлегший його рівень.

### Головне правило

**Оплаченим замовлення робить лише перевірений підпис.** Повернення покупця в браузері нічого
не доводить: параметрів там мінімум, підпису серед них може не бути, а ту саму адресу здатен
відкрити руками будь-хто. Тому «оплачено» ставиться тільки з `NOTIFY`-запиту шлюзу або з
відповіді на **наш власний** запит статусу.

Звідси випливає все інше: без переданої банку адреси `NOTIFY_URL` оплати не позначатимуться
автоматично, і магазин працюватиме напівсліпо.

### Підключення

1. **Договір і реквізити.** Банк видає Merchant ID, Terminal ID і доступ до тестового
   середовища. Технічна підтримка підключення — `044 461-85-92`.
2. **Ключі.** Магазин генерує їх сам у кабінеті шлюзу: приватний ключ лишається у вас і
   підписує запити, сертифікат UPC перевіряє відповіді про оплату. **Для тестового й робочого
   середовища сертифікати різні.**
3. **Адреси, які треба передати банку** (вони показані в Налаштуваннях готовими рядками):
   - `NOTIFY_URL` — `https://ваш-домен/pay/notify`
   - `SUCCESS_URL` і `FAILURE_URL` — обидві `https://ваш-домен/pay/return`

   Обидві адреси повернення однакові навмисно: сторінка сама зʼясовує, чим закінчилась оплата,
   і веде людину або до замовлення, або до повторної спроби.
4. **Налаштування** (адмінка → Налаштування → «Оплата карткою на сайті»): Merchant ID,
   Terminal ID, середовище, ключ, сертифікат — і галка «Приймати оплату карткою».

Поки не заповнено все, вибір «оплатити карткою» покупцю **просто не показується**: кнопка,
що веде в помилку на останньому кроці оформлення, коштує дорожче за її відсутність.

Кнопка **«Перевірити зʼєднання»** там же покаже, чи сходиться комплект ключів і чи вміє ваш
PHP ними підписати. Двох найчастіших помилок підключення — зіпсованого при копіюванні PEM і
сертифіката від іншого середовища — вистачає, щоб оплата не працювала взагалі, і ловляться
вони саме тут.

### Куди класти ключі

Приватний ключ можна вставити в поле налаштувань, але **надійніше покласти файлом**:

```
storage/keys/upc-private.pem     приватний ключ магазину
storage/keys/upc-test.crt        сертифікат тестового шлюзу
storage/keys/upc-prod.crt        сертифікат робочого шлюзу
```

Файл із теки завжди старший за збережене в налаштуваннях. Причина проста: ключ у базі
потрапляє в кожен її дамп і в кожну копію на ноутбуці, а `storage/` вебсервером не віддається
й у дамп не входить. Тека вже в `.gitignore` — у репозиторій ключі не поїдуть.

### Як це виглядає для покупця

1. В оформленні зʼявляється крок **«Оплата»**: «При отриманні» (як було) або «Карткою онлайн».
   Типовим лишається «при отриманні» — мовчазна зміна звички на «спершу заплатіть» відлякує
   більше людей, ніж приваблює зручність картки.
2. Після підтвердження замовлення — сторінка `/pay/{токен}` із сумою й кнопкою, далі захищена
   сторінка банку: Visa, Mastercard, Apple Pay, Google Pay, підтвердження 3D Secure.
3. Повернення на сторінку замовлення, де прямо сказано, що сталося з грошима.

**Замовлення створюється до оплати, а не після.** Тому якщо покупець закриє сторінку банку,
продавець побачить неоплачене замовлення й зателефонує, а не втратить його мовчки. Посилання
на оплату лишається робочим — заплатити можна й наступного дня, зі сторінки замовлення.

Кошик очищається в обох випадках: повторне оформлення з нього створило б **друге** замовлення
на ті самі товари.

### Спроб оплати буває кілька

Шлюз відхиляє повторний `OrderID` (код 412), а покупець, у якого не пройшла картка, майже
завжди пробує другу. Тому кожна спроба — окремий рядок у таблиці `payments` зі своїм номером
(`BOFU-260801-A3F2`, далі `…-2`, `…-3`), своїм кодом відмови й своєю долею.

У картці замовлення видно **всі** спроби, свіжі зверху. Коли покупець дзвонить «я ж уже
платив», відповідь майже завжди в коді відмови попередньої спроби, а не в останній.

### Фіскальний чек

Оплата карткою на сайті — така сама розрахункова операція, як картка біля каси, і чек за нею
обовʼязковий. Тому чек ставиться в чергу **одразу після оплати**, зі способом «Картка», щоб
Z-звіт зійшовся з випискою еквайєра. Точки без заведеної каси пропускаються мовчки — так само,
як у касовому продажу.

Вимикати галку «Пробивати фіскальний чек одразу після оплати» варто лише тоді, коли чеки за
онлайн-продажами пробиваються деінде: інакше продаж піде повз ДПС.

### Блокування коштів (преавторизація)

Необовʼязковий режим: гроші на картці покупця **блокуються**, але магазину ще не належать —
списати їх треба окремою дією в картці замовлення.

Навіщо: у замовленні з кількох магазинів останню банку може забрати хтось інший за хвилину до
вас. Заблоковані кошти дозволяють списати менше або не списати нічого, і покупцю не доведеться
чекати повернення.

Ціна: списання не можна відкладати надовго — банки розблоковують суму самі за 7–10 днів, і
тоді гроші треба брати заново. Списати можна менше за заблоковане або більше, але не більш ніж
на 20% (інакше шлюз відмовить кодом 508). Чек за блокуванням не пробивається — розрахунку ще
не було; він зʼявиться після списання.

### Повернення

У картці замовлення, кнопкою **«Повернути на картку»**. Повне повернення робиться реверсалом,
часткове — із сумою: саме воно потрібне, коли із замовлення скасували одну позицію.

Повернення через API вмикається банком **окремо** (без цього приходить код 455). Якщо в
платежі немає коду авторизації або RRN, кнопки не буде: без них шлюз повернення не приймає, і
робити його доведеться в кабінеті банку.

**Фіскальний чек повернення це не пробиває** — його роблять окремо, у блоці чеків. Чек
повертає той самий ПРРО, що й пробив продаж, і робити це двома різними діями безпечніше:
інакше один продавець повернув би гроші, а другий, не знаючи, повернув би чек ще раз.

### Права

| Що робить | Право |
|---|---|
| Бачить оплати в картці замовлення | `orders.view` (усі, хто бачить замовлення) |
| Питає шлюз про стан оплати | `orders.status` |
| Списує заблоковане, повертає гроші | `orders.refund` |

`orders.refund` навмисно **немає** в наборі ролі «Продавець»: помилка тут рухає чужі гроші в
обидва боки й виправляється лише в банку, а не натисканням «скасувати». Бачити, чи оплачене
замовлення, продавець при цьому може — на це права не треба.

### Як вимкнути оплату карткою

Одна галка: **Налаштування → «Приймати оплату карткою на сайті»**. Реквізити при цьому
лишаються на місці — вимкнення оборотне й нічого не стирає.

Що відбувається:

| | Після вимкнення |
|---|---|
| Крок «Оплата» в оформленні | зникає, замовлення оформлюються як до еквайрингу |
| Посилання `/pay/{токен}` | працює, але каже «продавець зателефонує й узгодить оплату» |
| Історія оплат у картках замовлень | лишається повністю |
| Повернення й списання заблокованих коштів | **працюють далі** |
| Оплата, яку покупець почав хвилину тому | **завершиться нормально** і зарахується |
| `pay:sync` у cron | тихо виходить, нічого не робить |

Останні три рядки — не дрібниці, а сенс усієї конструкції. Гроші, які вже пішли з картки,
вимикачем не зупиняються: відмовитись від повідомлення банку означало б лишити оплачене
замовлення неоплаченим, а заборонити повернення — заморозити чужі гроші. Тому вимикач
зупиняє **нові спроби**, а не вже проведені платежі.

Єдине, про що доведеться подбати руками, — **замовлення, які вже чекали оплати посиланням**.
Їх сайт показує поруч із самим вимикачем (і в `prod-check`), із номерами й посиланнями: цим
покупцям треба зателефонувати й узгодити оплату інакше. Самі замовлення живі, покупець бачить
«продавець зателефонує», нічого не ламається — але обіцянку заплатити карткою сайт більше не
виконає, і краще дізнатись про це від вас, ніж від тиші.

Вимикати оплату **стиранням ключів** не варто: без сертифіката неможливо перевірити підпис,
тож оплата, яка вже в дорозі, буде скасована, а гроші повернуться покупцю. Це безпечно, але
для нього виглядає як поломка. Галка робить те саме без цього побічного ефекту.

### Як перейти на іншого постачальника

Постачальник записується **в сам платіж**, а не читається з налаштувань при потребі — та сама
конструкція, що й у фіскальних чеках, і з тієї ж причини: **повернення робить той, хто прийняв
гроші**. Платіж, проведений через Raiffeisen, не повернеш через іншого еквайєра.

Практичні наслідки:

- Після переходу старі платежі лишаються робочими: звірка, списання й повернення йдуть на той
  шлюз і в те середовище (`test`/`prod`), у якому платіж було створено, а не в поточне.
- Платіж від постачальника, якого в збірці більше немає, не обробляється мовчки «кудись»:
  сайт відмовить із поясненням, що операції з ним доступні в кабінеті того постачальника.
- Перемикання тестового шлюзу на робочий — окремий випадок того самого. Тому **сертифікати
  краще класти файлами** (`storage/keys/upc-test.crt` і `upc-prod.crt`): тоді після
  перемикання лишається можливість перевірити відповідь по старій оплаті. У полі налаштувань
  сертифікат один — того середовища, що ввімкнене зараз.

Щоб додати другого постачальника, потрібні три речі: рядок у `Acquiring::PROVIDERS`, клас із
його протоколом і розгалуження за `$payment['provider']` у `sync` / `capture` / `refund`.
Решта сайту — оформлення, картка замовлення, чеки, звірка, права, сповіщення — про
постачальника не знає нічого й змінюватись не має.

### Звірка: `pay:sync` у cron

`NOTIFY` — головний і найнадійніший шлях, але не єдиний можливий: сервер міг лежати саме в ту
хвилину, брандмауер міг відкинути чужий IP, а на локальній машині публічної адреси немає
взагалі. Наслідок завжди один і найгірший з можливих: **гроші списані, а замовлення виглядає
неоплаченим**.

Тому раз на чверть години питаємо шлюз про ті спроби, з яких покупець пішов і не повернувся:

```
7,22,37,52 * * * * php /home/USER/site/bin/cli.php pay:sync
```

Відповідь застосовується так само, як `NOTIFY`: та сама перевірка сум, той самий чек, той
самий лист покупцю. Повтору не буде — позначка про оплату ставиться один раз.

Якщо firewall (Cloudflare тощо) закриває сайт, додайте в білий список IP шлюзу: `217.13.180.171`
для робочого середовища, `18.196.61.127`, `3.120.143.246`, `18.197.170.36` — для тестового.
Сам сайт цим адресам не довіряє (вони змінюються без нашого відома, і платіж, відкинутий через
новий IP, виглядав би як «гроші списались, замовлення не оплачене») — замком тут працює підпис.

### Перевірка на тестовому шлюзі

Тестове середовище має **власні** Merchant ID, Terminal ID, ключі й сертифікат. Перемикання
без заміни всього переліку дасть відмову з кодом 402 на першій же оплаті.

`php bin/cli.php prod-check` окремо кричить, якщо на бойовому сайті лишився тестовий шлюз:
оплати «проходять», замовлення позначаються оплаченими, покупці отримують товар — а грошей
немає взагалі. Це дзеркальна помилка до забутого токена тестової каси й така сама дорога.

На `localhost` шлюз до `NOTIFY_URL` не достукається — там перевіряйте оплату лише повертаючись
у браузері (сторінка сама спитає шлюз про стан).

### Що перевіряє набір тестів

`tests/acquiring.php` (105 перевірок, `php bin/cli.php test`) працює на справжній криптографії з
несправжніми ключами, які генеруються прямо в наборі. Найдорожчі помилки цієї інтеграції тихі,
і їх чотири:

1. **Рядок для підпису.** Одна зайва кома дає код 405, і покупець бачить «оплата не пройшла» на
   робочому сайті. Формат UPC неочевидний саме комами: відсутнє поле прибирає кому, але не
   крапку з комою.
2. **Підроблена відповідь.** Перевіряється не лише те, що правильний підпис проходить, а й що
   неправильний не проходить, і що чужа сума не проходить.
3. **Повторне зарахування.** Шлюз надсилає сповіщення двічі — двічі позначена оплата означала б
   два фіскальні чеки на один продаж.
4. **Копійки.** Сума підписується цілими копійками, і перетворення туди-назад через float не
   має її зрушити навіть на одиницю.

Окремо перевіряється те, що ламається не під час роботи, а під час **зміни рішення**:
вимкнена оплата не заважає завершитись уже початій і не блокує повернення по вчорашній;
платіж памʼятає свій шлюз і після перемикання середовища; платіж від чужого постачальника не
надсилається «кудись», а чесно відмовляє.

## Фіскальні чеки (ПРРО)

Продаж на касі фіскалізується тим самим рухом, яким оформлюється: продавець тисне «Оформити»,
і покупець отримує чек із ДПС. Решта замовлень — кнопкою в картці, бо гроші за них приходять
пізніше й не завжди через нас.

Дві речі влаштовані так навмисно й від них залежить усе інше.

**Постачальника ПРРО можна змінити.** Логіка чека — рядки, знижки, податкові групи, повернення,
черга, повтори — живе в `app/Core/Fiscal.php` і про Вчасно не знає нічого: вона складає
**нейтральний документ**, а перекладає його на мову конкретного ПРРО окремий маленький клас
(`VchasnoDoc`). Щоб додати Checkbox чи Cashalot, треба написати такий самий клас і дописати
рядок у `FiscalProvider::PROVIDERS`. Постачальник записується **в сам чек**: після переходу
старі чеки далі знають свого, бо повернення робить той самий ПРРО, що й продаж.

**Ключ підпису не обовʼязково віддавати в хмару.** Є три маршрути до каси, і вибирають їх
у три яруси: людина → її точка → загальні налаштування.

| Маршрут | Де ключ | Хто несе чек | Кому підходить |
|---|---|---|---|
| **Хмара постачальника** | у постачальника | наш сервер | найпростіше налаштувати |
| **Каса точки** | флешка чи папка на касовому ПК | агент, який сам стукає до сайту | магазин із касовим ПК; телефони працюють звідусіль |
| **Каса на цьому пристрої** | Device Manager у самого продавця | його ж вкладка, на `localhost` | продавець зі своїм ПК або телефоном |

У двох останніх **наш сервер до каси не ходить взагалі**, і назовні в магазині не відкрито
жодного порту. Тому чек там спершу стає **в чергу** — це нормальний стан, а не помилка, і на
екрані він так і називається.

### Що налаштувати (один раз)

1. **У кабінеті ПРРО**: торгова точка, каса і — найголовніше — **ключ касира**. У хмарному
   маршруті його завантажують у сховище кабінету; у двох інших — у Device Manager на тій
   машині, де він стоїть, і ключ звідти нікуди не йде.
2. **Постачальник і маршрут за замовчуванням** — адмінка → Налаштування → «Каса (ПРРО)».
3. **Точка з іншою касою** — Магазини → картка точки: свій маршрут, адреса Device Manager,
   назва каси в ньому, податкова група (потрібна, коли точка належить іншому ФОПу).
4. **Продавець зі своєю касою** — його профіль, блок «Моя каса». Це особисте налаштування,
   як і канали сповіщень: Device Manager стоїть на його пристрої, з його ключем.
5. **Податкова група за замовчуванням** — Налаштування. Береться, коли її немає ні в товарі,
   ні в магазину. Помилка тут не помітна одразу: чек пробʼється, а розбіжність спливе
   в податковому періоді.
6. **Кнопка «Перевірити зʼєднання»** покаже рядок каси: чи відповідає, чи вона **фіскальна,
   а не тестова**, і чи лежить ключ у сховищі. Пробного чека ми не пробиваємо — він справжній,
   іде в ДПС і скасовується лише поверненням.

**Податкова група береться в такому порядку**: своя в товарі (Каталог → товар) → типова
магазину → **власника точки** → загальна. Товарна попереду решти, бо підакцизне чи пільгове не
залежить від того, з якої полиці його взяли; власникова попереду загальної, бо ставка належить
платнику податків, а не приміщенню.

### Коли мережа — це кілька ФОПів

Два магазини можуть належати одному ФОПу, а третій — іншому (наприклад, дружині). Для покупця
це один сайт, для податкової — **два окремі платники**: свої ПРРО, свої ключі, свої декларації
і свої ліміти доходу, які перевищуються кожен окремо.

Для цього є розділ **Мережа → Власники (ФОПи)**: назва як у документах, ІПН, група єдиного
податку, ознака платника ПДВ, ставка для чеків, підпис під нічним Z-звітом і те, які точки
кому належать. Заводити нікого не треба, якщо платник один — усе працюватиме як раніше.

**Замовлення з товарами різних власників розпадається на частини, і кожна отримує свій чек від
свого ПРРО.** Це не обхід, а те, як і має бути: кожен фіскалізує свій товар своїм ключем.
Знижка ділиться між ними пропорційно, а в картці замовлення під назвою магазину написано, чий
це виторг.

⚠️ **Група єдиного податку — це НЕ податкова група чека.** Найдорожча помилка в усій інтеграції
саме тут: людина знає, що вона «на 3-й групі», і ставить `3` у поле ставки, де 3 означає
«ПДВ 20% + акциз 5%». Чеки пробиваються, все зелене, а в ДПС їде вигаданий податок. Тому
сторінка власників перевіряє поєднання й каже про це прямо; те саме робить `tests/owners.php`.
Не платник ПДВ — майже завжди `2 (Без ПДВ)`.

**Виторг за рік** на тій самій сторінці — управлінська цифра, а не декларація: у ній лише те,
що пройшло через сайт. Але саме її бракує, щоб вчасно побачити наближення до ліміту.

### Розрахунок за рахунком (IBAN)

Клієнт-ФОП чи юрособа не купить без документів: йому треба чимось обґрунтувати
платіж у своєму обліку. Тому в картці замовлення є блок **Оплата**, а в ньому — рахунок
на оплату й видаткова накладна.

**Документи виставляються на ЧАСТИНУ замовлення**, як і чек із накладною, і з тієї самої
причини: продавець тут — конкретний ФОП, власник точки, і саме його IBAN та підпис стоять
у бланку. Замовлення на два власники — це два рахунки від двох різних продавців.

**Це заодно вирішує грошове питання**, з яким не впорався б спільний кошик: гроші за
кожну частину йдуть одразу на рахунок того ФОПа, чий це товар. Ні агентських договорів,
ні заборон.

Реквізити (повна назва, IBAN, банк, адреса, підписант) заповнюються **у власника** —
Мережа → Власники. Поки їх немає, бланк відкриється, але скаже, чого бракує: іноді
реквізити дописують ручкою, і краще віддати неповний бланк, ніж не віддати нічого.

Бланк — звичайна друкована сторінка: браузер → «Друк» → «Зберегти як PDF». Бібліотеку PDF
у проєкт без залежностей ставити заради двох документів не варто.

⚠️ **Система не дасть виставити рахунок тому, кому цей ФОП продавати не має права.**
Друга група єдиного податку обслуговує населення й платників ЄП, але не юросіб і не ФОПів
на загальній системі — за такий продаж втрачають спрощену систему. Перша група торгує лише
населенню. Тому в блоці оплати вказують, **хто покупець**, і перевірка спрацьовує до того,
як документ поїхав клієнту.

**Стан оплати** там же: чим розраховуються і чи гроші вже отримані. Дата ставиться один
раз — важливий саме перший момент надходження, від нього рахують і відвантаження, і чек.

Чи потрібен ПРРО-чек при оплаті на рахунок — питання до бухгалтера: переказ з рахунку на
рахунок зазвичай не потребує, а оплата карткою через інтернет потребує. Якщо потрібен —
пробивається кнопкою з типом оплати «Безготівка».

**Чого система не вирішує — куди йдуть гроші при інших способах оплати.** Кошик один, платіж один, а чеки від двох
різних ФОПів. Якщо оплата приходить на один рахунок, а чек на частину виписав інший платник,
виторг за ПРРО не зійдеться з рухом коштів у обох. Варіанти: готівка в точці (тоді питання
немає), заборона змішувати товари різних власників в одному замовленні, або агентський
договір. Це рішення бухгалтера, а не програми.

### Каса точки: агент

На касовому ПК працює агент — `bin/agent/vchasno-agent.ps1` (Windows, нічого встановлювати не
треба) або `bin/agent/vchasno-agent.php` (Linux). Він раз на кілька секунд питає сайт «є що
пробити?», несе отримане тіло на `localhost:3939` і повертає відповідь як є. Про формат чека й
постачальника він не знає нічого — інакше кожну зміну довелося б розвозити по всіх касових ПК.

Налаштування — `agent.config.json` поруч зі скриптом:

```json
{ "Site": "https://ваш-сайт.ua", "Token": "ag_…", "Dm": "http://localhost:3939" }
```

Токен беруть в адмінці: **Магазини → картка точки → «Створити токен агента»**. Він показується
**рівно один раз** — у базі лишається лише хеш, тож перелік ключів до всіх кас мережі не
витягти навіть із дампа. Щоб агент працював постійно, поставте його в Планувальник завдань
Windows із тригером «при запуску компʼютера».

У картці точки та на сторінці каси видно, **чи виходив агент на звʼязок** і коли востаннє.

### Каса на цьому пристрої

Device Manager стоїть там же, де відкрита адмінка, тож запит несе сама вкладка: сайт віддає їй
готове тіло, вона кладе його на `localhost` і повертає відповідь. Ключ лишається на пристрої,
відкривати нічого не треба. Працює однаково на Windows і на Android із Device Manager.

⚠️ **Це єдине місце, яке треба перевірити на живому Device Manager.** Браузер, звертаючись зі
сторінки сайту на локальну адресу, спершу питає дозволу (CORS + Private Network Access). Наш
емулятор такі дозволи віддає, але **чи віддає їх справжній DM — з документації не видно**.
Якщо ні, цей маршрут із браузера не працює, і лишається «каса точки» через агента — на тому ж
самому ПК, з тим самим ключем. Перевіряється це за півгодини, щойно буде встановлений DM.

### Коли чек пробивається сам

Автоматично — рівно те, за що гроші вже отримали: **видача з рук у точці** з галкою «товар
віддано». На третьому кроці каси зʼявляється «Чим розрахувались» (готівка / картка) і поле
«Отримано готівкою» — каса одразу покаже решту, а після оформлення повторить її в повідомленні
разом із номером чека.

Замовлення з каси **на доставку так не пробивається**: його оплатять при отриманні, а чек по
післяплаті пробиває перевізник. Фіскалізувати тут означало б порахувати гроші, яких ще немає.

**Готівка округлюється до 10 копійок** — монет дрібніших в обігу немає. Округлення йде в чек
окремим рядком, а не тихою зміною ціни: покупець бачить, звідки взялась різниця, а в ДПС
товар коштує рівно стільки, скільки на полиці. На картку не діє. Вимикається в Налаштуваннях.

**Помилка чека не скасовує замовлення** — товар уже віддали. Вона стає гучним повідомленням
продавцю («ЧЕК НЕ ПРОБИТО»), записом в історії замовлення, сповіщенням «Чек не пробився»
(увімкнене за замовчуванням, на відміну від решти службових подій) і кнопкою в картці.

**Зміну відкривати не треба**: якщо вона закрита, каса відкриє її сама разом із першим чеком.
А от **закривати треба** — Z-звіт хоча б раз на добу вимагає закон.

### Чек у картці замовлення

Блок під позиціями кожної частини. Чек, як і накладна, належить **частині**: гроші отримала
конкретна точка своєю касою, тож замовлення на два магазини — це два продажі й два чеки.

- **«🧾 Пробити чек»** — для всього, що не пробилось саме: телефонних замовлень, самовивозу,
  який щойно забрали, і другої спроби після відмови.
- **«↩ Чек повернення»** — те, чим у ПРРО скасовують продаж. Дзеркалить чек: ті самі рядки,
  та сама сума, той самий вид оплати, **той самий постачальник і маршрут**. Рядки беруться з
  того, що надсилали, а не збираються заново: позиції могли передати в інший магазин, а
  повернення має бути дзеркалом чека. Часткових повернень немає — повертайте чек цілком і
  пробивайте новий на те, що лишилось.
- **«↻ Перепитати касу»** — про це нижче.
- **«✉ Надіслати чек покупцю»** — уміє лише хмарний маршрут: у Device Manager чек надсилає сам
  ПРРО в мить фіскалізації, і попросити його про це пізніше нема як. В інших маршрутах дайте
  покупцю посилання на електронний чек — воно поруч.

Скасували частину, а чек лишився пробитим — блок скаже про це окремо: гроші в ДПС є, товару в
покупця немає, і кнопка повернення поруч. Дві мітки, про які блок теж не мовчить: **тестова
каса** (чек без юридичної сили) і **офлайн** (чек справжній, у ДПС піде при звʼязку).

### Обірваний звʼязок і чому не буде двох чеків

Кожен чек має свою **незмінну мітку** (`tag`), і рядок у базі створюється **до** будь-якої
відправки, разом із тілом запиту. Далі чотири стани:

- **у черзі** — завдання складене й чекає на агента точки або браузер продавця;
- **відповіді немає** — каса змовчала. Чек **міг** пробитись, тож ми не пишемо «не вийшло» й не
  пробиваємо новий. Повтор іде з **тією самою міткою** — ПРРО впізнає за нею ту саму спробу й
  віддасть той самий чек. Це не наша вигадка: у Device Manager це називається транзакційним
  режимом і описане в їхній документації;
- **пробито** — є фіскальний номер;
- **помилка** — ПРРО відмовив по суті (не зійшлась сума, немає ключа), причина видна разом із
  деталями валідації.

Тому таймаут на запит — 25 секунд (при проблемах з АЦСК чи ДПС каса не відмовляє, а дотискає
запит), а повтори ставлять у cron:

```
*/5 * * * * php /home/USER/site/bin/cli.php vchasno:retry
```

Ця ж команда повертає в чергу завдання, які агент забрав і не повернув (вимкнули ПК, обірвався
інтернет). Повертати безпечно рівно тому, що мітка незмінна.

### Зміна, звіти, готівка (адмінка → Продажі → Каса)

Стан каси, зміна, готівка в скриньці, звʼязок із ДПС. Кнопки: відкрити зміну, X-звіт
(проміжний, нічого не закриває), Z-звіт (закриває зміну), службові внесення й видача готівки.

Там, де ключ у магазині, кнопки не «роблять», а **ставлять завдання в чергу** — і на екрані це
так і написано: службові завдання йдуть тією самою чергою, що й чеки, з тими самими станами.
Інакше Z-звіт довелося б робити руками на касовому ПК, а людина поїде додому й забуде.

Z-звіт варто поставити в cron на час, коли точка вже не продає:

```
50 23 * * * php /home/USER/site/bin/cli.php vchasno:z
```

Команда проходить **кожну** точку окремо (зміна належить касі) і сама вибирає, слати завдання
напряму чи ставити в чергу агенту.

### Товари: звірка з кабінетом

У чек ми передаємо назву, ціну, податкову групу й **коди** — артикул (`code`) і штрихкод
(`code1`). Саме коди зшивають наш товар із товаром у кабінеті ПРРО: без них звіт покаже
«Мед липовий 0.5» і «Мед лип. 0,5л» двома різними рядками, тобто одну продажу — двома
половинками.

**API для номенклатури у «Вчасно.Каси» немає** — товари в кабінеті ведуть руками або файлом
Excel. Тому обмін теж файлом, в обидва боки (адмінка → Каса → Товари):

- **наш каталог → кабінет**: кнопка вивантаження дає XLSX (або CSV) у форматі їхнього імпорту —
  рядок на кожну **фасовку**, бо каса продає банку, а не «мед узагалі». Податкова група в файлі
  завжди заповнена: порожня клітинка означала б для кабінету «без ставки», а не «як у магазину»;
- **кабінет → звірка**: у кабінеті Товари → Дії → Експорт, отриманий файл завантажити сюди.
  Колонки шукаємо **за підписами**, а не за порядком (шаблон між версіями кабінету
  змінюється), розуміємо xlsx і csv, win-1251 і UTF-8, кому й крапку з комою, а податкову
  групу — і числом, і словами («Без ПДВ», «20%»).

Зіставляємо за штрихкодом, потім за артикулом, і лише в останню чергу за назвою. **Збіг за
назвою позначається окремо і кодів не переносить**: «Мед 0.5» буває і липовий, і гречаний, а
помилковий штрихкод відправить сканер на чужий товар.

Кнопка «Перенести до себе» заповнює в наших товарах **лише порожні** поля: артикул, штрихкод,
податкову групу, УКТЗЕД. Заповнене не чіпає навіть тоді, коли воно розходиться — у нас теж є
артикули, і мовчазна заміна нашого коду чужим це найкоротший шлях до товару, який більше не
знаходить сканер. **Ціни не переносяться взагалі**: ціна — рішення магазину, а не запис у
чужому довіднику, і в кожної точки вона своя.

Читання й запис таблиць — `app/Core/Sheet.php`. Без бібліотек і без розширення `zip`: у проєкті
немає залежностей (його ставлять копіюванням), а `zip` вимкнений у багатьох збірках, включно з
XAMPP. Формат ZIP зібраний руками, deflate уміє сам PHP; коли розширення все ж є, користуємось ним.

### Як це перевірено

Живої каси в тестах бути не може — кожен чек справжній і скасовується лише поверненням. Тому в
`bin/dm-emulator.php` лежить **емулятор Device Manager**: він приймає ті самі поля, перевіряє
те саме (сума чека проти суми рядків, оплати проти округлення, податкові групи, абетку назв) і
відмовляє тими самими кодами, що описані в їхній документації.

```
php -S 127.0.0.1:3939 bin/dm-emulator.php
```

Набір `tests/fiscal_routes.php` піднімає його сам і ганяє через **справжній HTTP** усе, що може
зламатись: черга й забір завдань рівно один раз, повний шлях до каси й назад, повтор тією самою
міткою (і те, що другого чека з нього не виходить), відмова каси на зіпсованій сумі, чистка
назв, службові завдання, повернення завислих у чергу, повернення тим самим маршрутом після
зміни налаштувань, і те, що завдання «на пристрої» бачить лише свій продавець.
`tests/vchasno.php` окремо перевіряє арифметику чека на підміненому транспорті.

### Права

Два окремі права, бо це різні роботи:

- **«Пробивати фіскальні чеки»** (`orders.fiscal`, у ролі «Продавець» є) — чек і повернення в
  картці замовлення. Продавець працює лише зі **своїми** частинами;
- **«Каса: зміна, звіти, звірка товарів»** (`fiscal.manage`) — сторінка каси. Z-звіт закриває
  день усій точці, а звірка товарів переписує каталог, тож це вже не робота продавця.

## Тексти: узгодження, апостроф, лапки

Дрібниці, які ламаються тихо й тому винесені в правила, а не лишені на уважність.

**Числівник узгоджується з іменником** — `plural()` і `plural_n()` у `helpers.php`. Правило
одне на весь сайт: до цього воно жило всередині оформлення (для «2 товари»), а лічильники
на головній його не знали й писали **«1 авторських курсів»** у найпомітнішому рядку
сторінки. Пастка тут не в множині, а в одинадцяти–чотирнадцяти: 11 закінчується на 1, але
це «одинадцять курсів». Зафіксовано в `tests/format.php`.

**Апостроф — `ʼ` (U+02BC), не `'`.** Вітрина була набрана правильно, адмінка — ні, і
«зʼявиться» та «з'явиться» для пошуку й вивантаження в маркетплейси є різними рядками.
Вирівняно по всьому `app/` (63 випадки в 42 файлах). Виняток лише один і навмисний — у
`Shop::weightIsAttr()` перелічені **обидва** написання, бо в старих картках характеристику
«обʼєм» заводили звичайною лапкою.

**Лапки — «ялинки».** `Набір «Пасічник»`, а не `Набір "Пасічник"`: прямі лапки — ознака
тексту, який ніхто не вичитував, і на тлі Cormorant Garamond це видно одразу.

**Питання покупця й питання про курс — різні блоки.** Спільний список означав, що на
сторінці навчання висіло питання «чи можна повернути товар з магазину». Тепер `faq` — про
магазин (доставка, зберігання меду, кристалізація, самовивіз, повернення), `faq_course` —
про навчання. Порожній `faq_course` ховає весь розділ, а не лишає порожній заголовок.

## Пошук у шапці

Поле пошуку існувало й раніше — усередині згорнутої панелі «Фільтри» в каталозі. Щоб ним
скористатись, покупець мусив зайти в магазин, розгорнути фільтри й аж там знайти рядок.
Тепер пошук стоїть у шапці на кожній сторінці; на телефоні, де в шапці для нього немає
місця, він переїжджає першим рядком у мобільне меню.

Форма звичайна, `GET` на `/shop` — працює без JS і веде в той самий каталог, який уже вміє
шукати. Та сама адреса віддана Google як `SearchAction`.

## Адреси каталогу

Розділ живе у шляху — `/shop/med`, а не `/shop?cat=med`. Причина не в позиціях у пошуку
(Google давно нормально читає параметри), а в тому, що розділ каталогу — це окрема сторінка
зі своїм заголовком, описом і крихтами, тоді як `?cat=` описує фільтр. Фільтри параметрами й
лишились: `/shop/med?sort=price_asc` — та сама сторінка, уточнена.

Одного сегмента вистачає й для підрозділів: `slug` категорії унікальний на всю таблицю.

Форма адреси зібрана в `shop_url()` (для посилань) і `shop_path()` (для sitemap і крихт, які
самі додають префікс). Раніше рядок `'/shop?cat=' . $slug` був розсипаний по десятку
шаблонів і двох контролерах. Плутати ці два хелпери не можна з тієї ж причини, що
`abs_url()` і `asset_abs()`: подвійний базовий шлях дає `/bofu/bofu/shop/med`.

**Старі адреси не ламаються.** `?cat=` віддає **301** на новий шлях разом з усіма іншими
параметрами — інакше редирект зʼїдав би вибране сортування. Робити це варто **до** відкриття
сайту для індексації: поки `seo_noindex` увімкнений, переїзд не коштує нічого, після запуску
це вже міграція з ризиком.

**Неіснуючий розділ — 404**, а не мовчазний показ усього каталогу: інакше будь-яка описка в
адресі віддавала б «усі товари» під виглядом сторінки розділу, і пошуковик індексував би їх
сотнями копій.

## Перегляд фото (лайтбокс)

Мед у сотах, віск, шкіряні рукавиці купують очима — а роздивитись їх було неможливо:
мініатюри лише підміняли головне фото тим самим розміром.

Розмітка не переписується під кожну сторінку. Модуль (кінець `assets/js/app.js`) шукає
контейнери з `data-lightbox` і збирає всередині все, у чого є `data-full`. Так одна
поведінка дісталась і картці товару, і галереї на трьох сторінках, і дістанеться тому, що
зʼявиться потім.

Три деталі, які легко пропустити:

- **мініатюри складають список, але перегляду не відкривають** (`data-lb-skip`) — у них своя
  дія, підмінити головне фото. Відкриває клік по великому, і саме з того кадру, який людина
  зараз бачить (`data-lb-open`), а не з першого;
- **коли фото одне**, мініатюр немає — тоді список складає саме головне фото, а стрілки й
  лічильник ховаються: гортати нема чого;
- **вікно створюється при першому відкритті**, а не лежить у кожному документі: більшість
  відвідувачів фото не збільшує;
- **список збирається на кліку, а не при завантаженні** — галерея товару перебирається при
  виборі фасовки (див. наступний розділ), і список, знятий один раз, показував би кадри,
  яких на сторінці вже немає.

Керування: Esc закриває, ←/→ гортають по колу, свайп на телефоні (поріг 40 px, вертикальний
рух не гортає — ним прокручують), клік повз фото теж закриває. Фокус повертається туди,
звідки прийшли, і сторінка під вікном не їде від прокрутки.

## Фото варіантів

Досі галерея належала товару цілком: перемикач фасовки міняв ціну, вагу, артикул і
наявність, а картинка лишалась та сама. Для банки 0,5 і банки 1,5 це терпимо, для кольору —
ні: «оберіть колір» без кадру самого кольору не вибір, а здогад.

**Мітка на фото, а не поле у варіанта.** У `product_images` зʼявився `variant_id`; порожній
означає «кадр спільний». Поле у варіанта дало б йому рівно одну картинку, а колір показують
кількома — загальний план, фактура, деталь. Заразом стара база не переписується: усі наявні
фото лишились спільними й поводяться далі так, як поводились.

Порядок вирішує `Catalog::gallery($product, $variant)` — одне правило на всіх, і сервер, і
браузер беруть його звідти:

- **свої кадри попереду, спільні за ними.** Не «тільки свої»: товар з одним кадром на колір
  інакше втрачав би макро й упаковку, щойно покупець клікне колір;
- **чужі не показуються зовсім** — червона шапка в галереї, поки обрано синю, це не «більше
  фото», а помилка;
- **головне фото веде галерею, лише поки в фасовки немає своїх** — інакше покупець обирає
  колір, а бачить загальний план;
- **заглушка лишається крайнім випадком.** Фасовка без своїх і без спільних кадрів (усі
  фото розібрані по інших) показує головне фото товару: воно принаймні про цей товар.

**Головним стає перше спільне фото, а не просто перше.** Головне стоїть у каталозі, кошику
й у соцмережах, тобто представляє товар цілком, — кадр, знятий заради одного кольору, у цій
ролі обманює. Тому в адмінці кнопка «★ Головне» на закріпленому фото не показується: спершу
зніміть мітку.

**Кошик, каса й набори** беруть `Catalog::photo($product, $variant)` — фото обраної фасовки,
а коли свого немає, головне фото товару. Заглушка тут неприпустима: рядок мусить лишатись
впізнаваним завжди.

У браузері галерею перебирає `updatePhotos()` в `assets/js/app.js` — разом із ціною й
наявністю, з готового списку, що приходить у `BOFU_VARIANTS`. Розмітка при цьому одна:
блок мініатюр існує в товару з фасовками завжди, навіть коли зараз кадр один (тоді він
порожній і схований), — інакше його доводилось би створювати з JS, а це вже друга галерея.

**Адмінка:** картка товару → «Фотографії», під кожним фото список «спільне фото / назва
варіанта». Видалення варіанта не забирає його кадри з собою — вони знову стають спільними.

Перевіряється в `tests/variant_photos.php` (`php bin/cli.php test`).

## Правові сторінки, контакти й підвал

Умови продажу — частина товару, а не додаток до нього. Без них покупець не бачить, з ким
укладає договір, а закони «Про електронну комерцію» та «Про захист персональних даних»
прямо вимагають цієї інформації на сайті. Google Merchant Center без сторінок доставки й
повернення не пускає товари у безкоштовні картки.

Пʼять адрес, усі — один шаблон `home/legal.php` і один метод `Home::legal()`, бо
відрізняються вони лише текстом:

```
/delivery   Доставка              /privacy   Політика конфіденційності
/payment    Оплата                /offer     Публічна оферта
/returns    Обмін і повернення
```

Тексти лежать у блоках контенту (адмінка → Контент сайту → група «Контакти й правове») і
правляться без програміста. Вбудовані значення з `Seeder` — робочий каркас за українськими
нормами, а не готовий документ: оферту варто узгодити з юристом.

**Про повернення — окремо, бо тут легко пообіцяти незаконне.** Мед та інші харчові продукти
**належної якості обміну й поверненню не підлягають**: вони в переліку, затвердженому
постановою Кабміну №172. Обіцяти на них «14 днів на повернення» не можна. А от товар
неналежної якості — пошкоджений, протік, не той — міняти зобовʼязані, і саме це в тексті
розписано докладно.

**Реквізити не вигадуються.** `legal_entity` за замовчуванням порожній, і сторінка чесно
пише, що реквізити не заповнені, замість підставити вигадану назву ФОП у текст договору.
Заповніть перед запуском: назва як у виписці, РНОКПП або ЄДРПОУ, адреса реєстрації.

### Оферта й політика конфіденційності живуть у коді

`app/Core/LegalText.php`. Обидва документи стандартні — їхній зміст диктують закон і GDPR,
а не бізнес, — тому вони показуються самі, без жодного налаштування, і оновлюються разом
із сайтом.

Блок контенту при цьому лишається **старшим**: щойно власник напише свій текст, показується
він. Порожній блок означає «беремо вбудований», а не «сторінка порожня» — саме тому підказка
в адмінці починається з «ЗАЛИШТЕ ПОРОЖНІМ».

Доставка, оплата й повернення сюди не входять навмисно: там кожен рядок залежить від
конкретного бізнесу — перевізники, строки, пороги безкоштовної доставки. Вбудований
«правильний» текст для них був би вигадкою про чужу роботу.

Що покрито: **Україна** — ЦК (ст. 633, 641, 642: публічний договір, оферта, акцепт діями),
закони «Про електронну комерцію» (ст. 7, 11), «Про захист прав споживачів» (ст. 8, 9, 13),
«Про захист персональних даних», постанова КМУ №172. **ЄС** — GDPR: підстави обробки
(ст. 6), права субʼєкта (ст. 15–22), передача до третіх країн (ст. 44–49), скарга (ст. 77).

Одержувачі даних у політиці перелічені не «типові», а справжні — ті, куди код реально
ходить: `api.novaposhta.ua`, `kasa.vchasno.ua` (і далі ДПС), `accounts.google.com`,
`api.telegram.org`, `chatapi.viber.com`, карти Google на сторінці «Де нас знайти».

Міграція 40 прибирає з бази старий чорновик, щоб сторінка взяла вбудований текст, — але
**лише** чорновик, який туди поклали ми. Впізнає його за першими словами; якщо власник уже
написав своє, міграція не чіпає нічого. Перевірено обидва випадки.

Це не заміна юристу. Найтонше місце — повернення: для харчових продуктів діє постанова
КМУ №172, для дистанційної торгівлі — ст. 13 Закону «Про захист прав споживачів» із власним
переліком винятків. Ці норми накладаються, і однозначного трактування для меду вбудований
текст дати не може.

**Підвал** із трьох рядків став чотирма колонками: хто ми → контакти → покупцеві → про нас,
під ними правовий рядок. Порожні значення не показуються — поки телефон не вписали, рядка
просто немає, а не «Телефон: —».

**Графік роботи точок** живе в колонці `stores.hours` (адмінка → Магазини). Один рядок, а
не сім полів на дні тижня: точок кілька, графік простий, а конструктор розкладу коштував би
дорожче за користь. Той самий рядок іде в розмітку `Store` для Google.

## Розмітка для пошуковиків

`app/Core/JsonLd.php`. Було лише `Product`; стало шість видів, і кожен закриває свій тип
результату у видачі:

| Розмітка | Де | Що дає |
|---|---|---|
| `Organization` | усі сторінки | зводить сайт, YouTube і соцмережі в одну сутність (`sameAs`) |
| `WebSite` + `SearchAction` | усі сторінки | рядок пошуку по сайту прямо у видачі Google |
| `Product` | картка товару | безкоштовні картки товарів у Google Shopping |
| `BreadcrumbList` | товар, каталог, курси, магазини | шлях замість голої адреси в результаті |
| `FAQPage` | головна, курси | питання розкриваються прямо у видачі |
| `Course` | курси | картка курсу |
| `Store` | «Де нас знайти» | адреса, телефон і графік у картці компанії |

Три правила, спільні для всіх методів класу:

- **порожнє поле не віддаємо взагалі.** Google читає `"brand": ""` як помилку розмітки, а
  не як «бренду немає». Тому кожен блок проходить `clean()`, а `tag()` не друкує нічого,
  якщо після чистки лишились самі `@context` і `@type`;
- **адреси лише абсолютні.** Відносні Google мовчки ігнорує. Для сторінок — `abs_url()`,
  для файлів — `asset_abs()`. Плутати їх не можна: `asset()` уже додав базовий шлях, і
  пропускати результат ще раз через `abs_url()` дає `/bofu/bofu/assets/…`;
- **нічого не вигадуємо.** `aggregateRating` немає й не буде, поки на сайті немає жодного
  відгуку: розмітка, яка обіцяє зірки, яких немає на сторінці, — привід для ручних санкцій.

У `Product` додано те, без чого Google не пускає позицію в картки товарів: `sku`, `gtin13`
(зі штрихкоду, якщо він 13-значний), `weight` і `priceValidUntil`. Останнє обовʼязкове —
без нього пропозиція вважається простроченою; ставимо рік уперед, бо ціни на сайті
безстрокові.

**Описи сторінок** більше не спільні. Порожній `meta_description` падав у глобальний
`seo_description`, і Google бачив десяток сторінок з однаковим описом — для нього це
дублікати. Тепер свій опис мають категорії (з підрахунком позицій), курси, магазини,
диплом і всі правові сторінки.

## Вага товару й ціна за 100 г

Колонка `products.weight` існувала з часів накладних Нової Пошти, але покупцеві її не
показували. Виходило «Мед у сотах — 600 грн» без відповіді на питання «скільки його там»:
порівняти ціну неможливо, а без порівняння 600 грн виглядають просто дорого.

Тепер вага стоїть у характеристиках, а під ціною — рядок «51,43 грн / 100 г». Це той
рідкісний випадок, коли чесна цифра здорожчує товар в очах покупця, а не здешевлює.

Три правила, зафіксовані тестом `tests/format.php`:

- **вага належить фасовці.** Банка 0,5 і банка 1,5 коштують різне й важать різне, тож при
  виборі варіанта JS переставляє і вагу, і ціну за 100 г — так само, як наявність;
- **дрібні фасовки не ділимо.** «За 100 г» для пляшечки 30 мл — цифра, якої покупець ніколи
  не купить; рядок просто ховається;
- **вагу не дублюємо.** Якщо вага вже описана характеристикою («Вага: 350 г» — а так її
  заводили роками), свій рядок не виводимо: два однакові рядки підряд читаються як помилка.

Подача теж має правила: `weight_fmt()` показує 350 г, а не 0,35 кг (покупець меду міряє
грамами), і зрізає нулі лише там, де вони справді зайві — перша реалізація перетворювала
200 г на 2 г.

## Швидкість завантаження

Перше відкриття головної з нового пристрою важило **607 КБ у 18 запитах**. Заміряно в
браузері (`performance.getEntriesByType('resource')`), а не на око. Стало **~392 КБ**, і —
що важливіше — та частина, яка блокує перший показ сторінки, зменшилась учетверо.

**Стиснення й кеш статики** (кореневий `.htaccess`). Сервер не стискав нічого: CSS їхав
як 97 КБ замість 25, HTML — як 30 замість 7.5. Два блоки під `<IfModule>`, тож на хостингу
без цих модулів файл лишається робочим.

Одна пастка варта згадки: звичний `AddOutputFilterByType` належить **mod_filter**, а не
mod_deflate. На сервері, де є один без іншого, обгортка `<IfModule mod_deflate.c>` його
пропускає — і сайт після цього віддає 500 на кожен запит. Тому тут `SetOutputFilter` у
`<FilesMatch>`: це директива ядра, і їй достатньо самого deflate.

Кеш: css і js на рік (їхні адреси містять час зміни файлу — `asset_v()`, тож нова версія
має нову адресу), шрифти на рік (вони не змінюються ніколи), зображення на тиждень —
фото товару підмінюють тим самим імʼям, і рік означав би рік старої картинки.
Повторний візит після цього важить **13 КБ** замість 607.

**Значок вкладки.** `avatar.png` — PWA-іконка 400×400 на 137 КБ — стояв у `<link rel="icon">`
і в шапці сайту розміром 34×34. Тобто на кожній сторінці вантажилось 137 КБ заради
квадратика в куті вкладки: більше, ніж усі скрипти сайту разом. Поруч лежить `favicon.png`
64×64 на 5 КБ; велика лишається там, де вона справді велика — manifest, apple-touch-icon,
og:image.

**YouTube більше не гальмує головну.** Список відео кешується на годину, але оновлював його
той відвідувач, який першим прийшов після протухання кешу, — і чекав, поки сервер зробить
**16 послідовних запитів** до YouTube (RSS плюс окремий HEAD на кожне з 15 відео, щоб
відрізнити Shorts). Це і були ті «іноді сайт відкривається кілька секунд».

Тепер оновлення живе в cron, а сторінка віддає те, що лежить, навіть протухле:

```
30 * * * * php /home/USER/site/bin/cli.php yt:refresh
```

Хвилина не нульова навмисно: о рівній годині на shared-хостингу стартують крони всіх
сусідів одночасно. Застарілий на годину список відео — дрібниця; сторінка, що вантажиться
пʼять секунд, — ні.

**Що лишилось найважчим — шрифти: 305 КБ, 13 файлів.** Це чотири накреслення Manrope і три
Cormorant, кожне у двох підмножинах (кирилиця + латиниця, бо назва бренду латиною). woff2
уже стиснутий, гзипом його не зменшити — лише відмовою від частини накреслень, а це вже
зміна вигляду сайту, тож зроблено не було.

## Безпека

- Ціни, знижки й підсумок рахуються **тільки на сервері** з БД. З браузера приймаються лише
  `product_id`, `variant_id`, `qty` — підмінити ціну через POST або DevTools неможливо.
- **Ролі.** Адмін веде сайт цілком. Продавцю доступні лише замовлення його магазинів та
  **ціни й залишки цих магазинів**; картку товару (назва, опис, базова ціна, варіанти, фото),
  медіа-бібліотеку, налаштування, користувачів, акції та контент змінює лише адмін.
  Перевірка — на сервері (`Products::save()`, `Auth::requireAdmin()`), форма її лише повторює.
- **Доступ до точки закінчується разом із роллю.** Прив'язка людини до магазину
  (`seller_stores`) існує лише поки в неї є роль продавця: знімають роль — вона зникає з усіх
  точок, і повернення ролі доступу **не відновлює**, магазини треба призначити наново
  (`Users::saveStores()`). Інакше рядок прив'язки пережив би звільнення й одна галка,
  повернена через рік зовсім для іншої точки, мовчки відкрила б старі залишки й замовлення.
- **Файли поза доступом ззовні**: `app/`, `bin/`, `storage/` (сесії, логи, SQLite) і `config*.php`
  закриті власними `.htaccess` — вони працюють навіть якщо `mod_rewrite` вимкнений.
  У `assets/uploads/` заборонено віддавати скрипти; фото ще й перекодовуються через GD.
- Дані, що потрапляють усередину `<script>` (JSON-LD, варіанти товару), виводяться через
  `json_js()` — назва товару з `</script>` не може розірвати тег.
- Обовʼязковий телефон: номер нормалізується до `+380XXXXXXXXX` (або E.164), сміття не проходить.
  Правило одне на весь сайт (форми, вхід за номером, гейт) — `AuthTokens::normPhoneAny`,
  зафіксоване тестом
  `tests/phone.php`. У браузері воно продубльоване (`assets/js/app.js`), щоб людина бачила
  помилку одразу, а не після перезавантаження сторінки: **міняючи одне, міняйте й друге** —
  розʼїзд цих двох місць виглядає як «форма не приймає правильний номер».
- Сторінка «замовлення прийнято» відкривається за випадковим токеном, а не за номером замовлення.
- Обмеження частоти (таблиця `rate_hits`, за IP): оформлення 15/год, вхід через месенджер 20/год,
  код на телефон 10/год, довідник Нової Пошти 300/год, перевірка диплома 40/год. У формі checkout
  є honeypot-поле для ботів.
- **За Cloudflare або балансувальником** увімкніть у `config.local.php` `'trust_proxy' => true`,
  інакше всі відвідувачі рахуватимуться як один IP. Без проксі лишайте `false` — інакше ліміт
  обходиться підробкою заголовка `X-Forwarded-For`.
- **Заголовки безпеки** (`Core/Security.php`, шлються найпершими в `App::run()`): `nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` (з камери — лише свій домен,
  вона потрібна для сканера) і CSP. Зафіксовані тестом `tests/security.php`.
- **HSTS вимкнений за замовчуванням** — вмикається `'hsts' => true` у `config.local.php`.
  Вмикайте лише коли HTTPS працює на **всьому домені**: заголовок діє на домен цілком і
  памʼятається браузером місяцями, тож помилкою можна покласти сусідній сайт, і швидко це
  не відкотити.

### Чого CSP поки що не закриває

`script-src` містить `'unsafe-inline'`. Це означає: якщо кудись усе-таки вдасться вставити
`<script>`, CSP його **не зупинить**. Причина — у шаблонах вісімнадцять інлайнових `<script>`
і близько двадцяти `onclick`, і сувора політика просто поклала б сайт.

Решта директив при цьому не декоративна й працює навіть так: `base-uri` не дає підмінити
`<base>` і перенаправити всі відносні шляхи на чужий домен, `form-action` не дає вставленій
формі відправити дані назовні, `connect-src` не лишає вкраденому куди поїхати, `object-src`
прибирає цілий клас старих векторів.

Шлях до суворої політики, якщо колись знадобиться: видавати нонс на запит, дописати його
кожному `<script nonce="…">`, перенести `onclick` у слухачі подій — і прибрати `'unsafe-inline'`.
Робота на пів дня й помітний ризик щось непомітно зламати, тож робити її варто окремо, а не
перед переїздом на бойовий сервер.

## Перенос на бойовий сервер: покроково

Розділяємо за природою речей, а не за зручністю:

| Що | Чим переносимо | Чому саме так |
|---|---|---|
| Код | **git** (GitHub → cPanel Git Version Control) | оновлюється постійно, має історію, відкочується |
| База | **вручну**, підготовленими запитами | демо-дані сідера в прод не можна |
| Фото з `assets/uploads/` | **Диспетчер файлів або FTP** | вони в `.gitignore` навмисно |

Фото через git не переносимо не тому, що «засмітять», а тому, що це **контент, а не
код**: він народжується на бойовому сервері, коли ви завантажуєте картку товару. Якби
він жив у репозиторії, кожне завантаження фото з адмінки вимагало б коміту, а
розгортання — затирало б те, що завантажили після останнього пуша. `.gitignore` цю межу
вже проводить, і переносити її не варто.

### 1. Файли

1. cPanel → Git Version Control → налаштувати клон (див. розділ вище).
2. **Pull or Deploy → Update from Remote → Deploy HEAD Commit.**
3. Перевірити, що в `public_html/bofu` є `.htaccess` (Диспетчер файлів показує приховані
   файли після Налаштування → «Показувати приховані файли»). Немає — розгортання
   пішло не так, далі йти не можна.

Далі кожне оновлення — це `git push` локально й дві кнопки в cPanel. Більше нічого.

### 2. База

1. cPanel → MySQL Databases → створити **порожню** базу й користувача, дати всі права.
2. Створити на сервері `config.local.php` з цими доступами (див. «Перенос на HostIQ», п. 4).
3. cPanel → Terminal:
   ```bash
   cd ~/public_html/bofu && php bin/cli.php migrate
   ```
   Створить таблиці **без демо-даних**. Важливо зробити це до першого відкриття сайту:
   `App::dbReady()` бачить порожню базу як «перший запуск» і сам запускає сідер із
   демо-товарами й демо-адміністратором.
4. Наповнити довідники своїми запитами (категорії, товари, магазини) або руками
   в адмінці — після кроку 3.

**Якщо демо-дані все-таки з'явились** (сайт відкрили раніше, ніж виконали `migrate`,
і `App::dbReady()` прийняв порожню базу за перший запуск) — чистити треба однією
командою разом із міграцією, інакше між ними лишається вікно, у яке встигає будь-яка
відкрита вкладка чи бот, і демо-дані повертаються:

```bash
cd ~/public_html/bofu && php bin/cli.php wipe НАЗВА_БАЗИ && php bin/cli.php migrate
```

`wipe` видаляє **всі** таблиці бази й вимагає її назву аргументом — не прапорець
`--force`, який дописують не читаючи, а саме назву: її треба свідомо подивитися в
`config.local.php` і надрукувати, і на чужій базі вона не збігається. Без правильної
назви команда нічого не робить.

### 3. Перший адміністратор

Тут єдине неочевидне місце всього переносу. Будь-який вхід — за поштою чи через Google —
створює людину **покупцем**, і правильно робить: інакше будь-хто, хто натиснув «Увійти»,
ставав би адміністратором. Але на порожній базі це замикає коло: щоб роздати ролі, треба
вже мати доступ до адмінки.

Розмикається так:

1. Відкрити сайт, **увійти своєю поштою** (кодом із листа або через Google). Акаунт
   створиться покупцем.
2. cPanel → Terminal:
   ```bash
   cd ~/public_html/bofu && php bin/cli.php grant-admin ваша@пошта
   ```
3. Перезайти на сайт. Тепер доступна адмінка.

Команда працює лише з консолі — тобто в того, хто має доступ до хостингу. З браузера
підвищити собі права нема як.

### 4. Фото

Скопіювати вміст локальної `assets/uploads/` у `public_html/bofu/assets/uploads/`
через Диспетчер файлів (зручно ZIP-ом: завантажити архів, потім «Видобути»). Права на
теку — 755. Розгортання git ці файли не чіпає: вони не в репозиторії.

### 5. Перевірка

```bash
cd ~/public_html/bofu && php bin/cli.php prod-check
```

Доки не покаже «Готово до бойового сервера» — на сайт нікого не пускаємо. Далі зняти
`seo_noindex` в Налаштуваннях, щоб сайт побачили пошуковики.

### 6. Каса (ПРРО): вмикають в останню чергу і в три заходи

Чек — **єдина дія на сайті, яку не можна відкотити**. Скасувати його можна лише чеком
повернення, і обидва вже в ДПС. Тому касу вмикають, коли решта сайту вже працює, і не
одним рухом.

#### Захід 0. Код (нічого не вмикає)

Оновлення коду касу **не вмикає**: поки не обрано маршрут, інтеграція мовчить — не
ходить у мережу, не пише в базу, не показує ні пункту меню, ні полів оплати на касі.
Продаж іде рівно так, як ішов учора.

1. Локально: `git push` (код має бути в `main`).
2. cPanel → Git Version Control → **Update from Remote** → **Deploy HEAD Commit**.
3. Схема оновиться сама на першому ж запиті. Явно — так:
   ```bash
   cd ~/public_html/bofu && php bin/cli.php migrate
   ```
   Міграція 35 лише **додає**: таблицю `fiscal_receipts` і стовпці в `stores`, `users`,
   `products`. Нічого не переписує й не видаляє.
4. `php bin/cli.php prod-check` — рядок «Каса (ПРРО): жодного маршруту не налаштовано»
   на цьому кроці **правильний**, це не помилка.

#### Захід 1. Тестова каса

Тестовий ПРРО створюється в кабінеті сам і **в ДПС нічого не надсилає** — на ньому
можна пробити скільки завгодно чеків безкарно.

1. У кабінеті ПРРО: зареєструватись, додати компанію по ключу ЕЦП, узяти **тестову** касу.
2. Обрати маршрут:
   - **хмара** — токен у Налаштування → «Інтеграції та SEO»;
   - **каса точки** — Магазини → картка точки: маршрут «Каса точки», адреса
     `http://localhost:3939`, назва каси в Device Manager; далі кнопка
     **«Створити токен агента»** (показується один раз) і встановлення агента — див. нижче;
   - **каса на пристрої** — профіль продавця, блок «Моя каса».
3. Налаштування → «Каса (ПРРО)»: податкова група за замовчуванням. Помилка тут не
   помітна одразу — чек пробʼється, а розбіжність спливе в податковому періоді.
4. Кнопка **«Перевірити зʼєднання»**: має бути «каса … відповідає» (хмара) або
   «Точки працюють без хмари» (решта маршрутів).
5. **Пробити один продаж** на касі з галкою «товар віддано». У картці замовлення мають
   зʼявитись номер чека, посилання на електронний чек і позначка **«ТЕСТОВА каса»**.
6. **Пробити на нього чек повернення** — переконатись, що й це працює.
7. Окремо перевірити **округлення готівки**: продати щось на суму з копійками
   (наприклад 99.99) і глянути, що в чеку є рядок округлення, а оплата — 100.00.
   Це єдине місце, де їхня документація суперечлива, і саме тут це видно.
8. Якщо маршрут «каса на пристрої» — перевірити, що чек пробивається **з телефона теж**.
   Якщо браузер не пускає вкладку на `localhost` (див. розділ «Фіскальні чеки»),
   перемкніть точку на «касу точки» з агентом: той самий ПК, той самий ключ.

#### Захід 2. Бойова каса

1. **Ключ касира**: у хмарному маршруті — у сховище кабінету; у решті — у сам Device
   Manager на тому ПК (флешка або папка). Без ключа токен працює, а підписати чек нема кому.
2. Замінити тестовий ПРРО на **фіскальний** (токен у Налаштуваннях чи назву каси в DM).
3. `php bin/cli.php prod-check` — має бути «каса … відповідає» **без слова ТЕСТОВА**.
   Якщо там «токен ТЕСТОВОЇ каси» — далі не йти: чеки не потраплять у ДПС.
4. Cron (cPanel → Cron Jobs):
   ```
   */5 * * * * php /home/USER/public_html/bofu/bin/cli.php vchasno:retry
   50 23 * * * php /home/USER/public_html/bofu/bin/cli.php vchasno:z
   ```
   Перший добирає чеки, на які каса не відповіла, і повертає в чергу завислі. Другий
   закриває зміну — закон вимагає щодоби, інакше каса перестане приймати чеки посеред дня.
5. **Перший справжній продаж — на дрібну суму, своїми грошима**, і одразу чек повернення
   на нього. Це і перевірка, і спосіб не залишити в звітності випадкових грошей.

#### Агент на касовому ПК (маршрут «каса точки»)

1. Встановити **Device Manager** (`wiki-kasa.vchasno.ua` → Packages), додати в ньому ПРРО
   й завантажити ключ — з флешки або з папки. Ключ лишається на цій машині.
2. Скопіювати теку `bin/agent/` на цей ПК (з репозиторію або з `public_html/bofu`).
3. Створити поруч `agent.config.json`:
   ```json
   { "Site": "https://ваш-сайт.ua", "Token": "ag_…", "Dm": "http://localhost:3939" }
   ```
   `Token` — той, що показала адмінка при створенні. Він показується **один раз**.
4. Перевірити руками:
   ```
   powershell -ExecutionPolicy Bypass -File vchasno-agent.ps1
   ```
   У вікні має зʼявитись «Агент запущено», а в адмінці (Магазини → картка точки) —
   «агент на звʼязку».
5. Поставити на автозапуск: Планувальник завдань Windows → тригер «При запуску
   компʼютера», «Виконувати незалежно від того, чи ввійшов користувач», дія — той самий
   рядок запуску.
6. `prod-check` показує мовчазного агента **критичною** позначкою: точка, яка приймає
   гроші й не пробиває чеків, — це не попередження.

#### Відкат

Код відкочується як завжди: cPanel → Git → розгорнути попередній коміт. Схема 35 нічого
не видаляє, тож старий код працює з новою базою — нові стовпці він просто не читає.

Чого відкат **не скасує** — уже пробитих чеків: вони в ДПС. Якщо продаж був помилковий,
його скасовують чеком повернення, а не відкотом.

#### Чого не робити

- Не вмикати бойову касу в п'ятницю ввечері: перша ж відмова ПРРО чекатиме до понеділка.
- Не пропускати захід 1. Тестова каса безкоштовна, а перший бойовий чек — назавжди.
- Не лишати Z-звіт без cron: через добу каса просто перестане приймати чеки.

### 7. Оплата карткою: після каси і в два заходи

Порядок не випадковий: успішна онлайн-оплата **ставить чек у чергу**. Увімкнути еквайринг
раніше за ПРРО означає почати приймати гроші, за якими нікому пробити чек.

Повний опис — у розділі «Оплата карткою» вище; тут лише порядок дій.

#### Захід 1. Тестовий шлюз

1. У Налаштуваннях: Merchant ID, Terminal ID **тестові**, середовище «тестовий шлюз»,
   тестовий ключ і тестовий сертифікат.
2. Передати банку адреси `https://ваш-домен/pay/notify` (NOTIFY_URL) і
   `https://ваш-домен/pay/return` (SUCCESS_URL і FAILURE_URL). Без першої оплати не
   позначатимуться самі.
3. Кнопка «Перевірити зʼєднання» — рядок «Оплата карткою» має бути без хрестика.
4. Оформити замовлення на себе й оплатити тестовою карткою (банк дасть номери).
   Перевірити три речі: замовлення стало оплаченим **без вашої участі** (значить, NOTIFY
   дійшов), у картці видно код авторизації та RRN, чек пробився.
5. Cron:
   ```
   7,22,37,52 * * * * php /home/USER/public_html/bofu/bin/cli.php pay:sync
   ```
   Він добирає оплати, про які NOTIFY не дійшов. Без нього такий платіж лишиться
   «неоплаченим» назавжди, хоча гроші вже списані.

#### Захід 2. Робочий шлюз

1. Замінити **весь** комплект: Merchant ID, Terminal ID, ключ, сертифікат — вони в
   робочому середовищі інші. Перемкнути середовище на «робочий шлюз».
2. `php bin/cli.php prod-check` — рядок «Оплата карткою» має казати «робочий шлюз».
   Якщо там «увімкнено ТЕСТОВИЙ шлюз» — далі не йти: оплати проходитимуть, замовлення
   позначатимуться оплаченими, а грошей не буде взагалі.
3. **Перша справжня оплата — на дрібну суму, своєю карткою**, і одразу повернення на неї.
   Це перевіряє обидва напрямки руху грошей і те, що банк увімкнув повернення через API.

#### Чого не робити

- Не вмикати оплату, поки не передані адреси банку: кожен платіж доведеться підтверджувати
  руками, і про половину з них ви дізнаєтесь зі скарг.
- Не лишати приватний ключ у базі, якщо є доступ до файлів: `storage/keys/upc-private.pem`
  не потрапляє в дампи, а поле налаштувань — потрапляє в кожен.
- Не вимикати «Пробивати фіскальний чек одразу після оплати», якщо чеки більше нікому
  пробивати: продаж піде повз ДПС.

## Перевірка готовності: `php bin/cli.php prod-check`

Показує, що заважає пускати на сайт покупців. Нічого не змінює — виправлення завжди рішення
людини: те, що на локальній машині помилка, на тестовому стенді буває навмисним.

Перевіряє: залишок ключа `demo_login` і показ помилок, режим, наявність `config.local.php`, HSTS,
демо-користувачів `@bofu.local` і демо-магазини із сідера, чи лишився **справжній**
адміністратор, координати точок, тестові замовлення, ключ карти, заборону індексації,
права на теки запису і — окремо — чи доїхали всі `.htaccess`.

Дві перевірки тут дзеркальні одна одній і найдорожчі: **тестова каса** (чеки пробиваються,
номери є, а в ДПС не потрапляє нічого) і **тестовий шлюз оплати** (оплати проходять,
замовлення позначаються оплаченими, а грошей немає взагалі). Обидві виявляються не одразу,
тому обидві — «не можна».

Код виходу ненульовий, якщо є хоч одне «не можна», тож перевірку можна ставити останнім
кроком розгортання.

Порядок дій перед запуском:

1. `php bin/cli.php prod-check` на сервері (cPanel → Terminal, або через SSH).
2. Закрити все, що позначене `✗`.
3. Переглянути `!` — це не блокери, але кожен варто прочитати.
4. Повторити, доки не лишиться «Готово до бойового сервера».

## PWA (додаток на телефон)

Відкрийте адмінку на телефоні → меню браузера → «Додати на головний екран».
Кнопки «Встановити додаток» і «Увімкнути пуші» є в бічному меню адмінки.

## Перенос на HostIQ (коли буде готово)

1. Експортуйте базу: `docker exec starvud-mysql mysqldump -ustarvud -p starvud > dump.sql` (пароль — DB_PASSWORD з `.env`)
2. У cPanel створіть базу MySQL і імпортуйте dump.sql через phpMyAdmin.
3. Скопіюйте файли проєкту в `public_html` (FTP або File Manager).
4. Створіть `config.local.php` з доступами до бази хостингу:
   ```php
   <?php return ['db' => ['host' => 'localhost', 'port' => 3306,
     'database' => 'xxx_bofu', 'username' => 'xxx_user', 'password' => '...']];
   ```
   Ключа `demo_login` тут бути не має — самої функції вже немає.
5. Увімкніть SSL (безкоштовний у HostIQ) — запрацюють Web Push і Google OAuth.
6. Перевірте, що `https://ваш-домен/config.php`, `/storage/`, `/app/` віддають 403 —
   якщо ні, у хостингу вимкнений `AllowOverride` і `.htaccess` не діють.
7. Схему бази оновлювати не треба: `App::dbReady()` викликає `Schema::upgrade()` на
   кожному запиті, тож перше ж відкриття сайту доводить базу до поточної версії.
8. Карту точок продажу увімкніть окремо — див. розділ нижче.

## Оновлення сайту через cPanel → Git Version Control

Замість заливати файли по FTP щоразу: cPanel тримає власний клон репозиторію,
забирає з GitHub нові коміти й розкладає їх у теку сайту. Що саме розкладати —
описано в `.cpanel.yml` у корені проєкту.

### Налаштування (один раз)

1. **cPanel → Git Version Control → Create.**
   - *Clone a Repository*: увімкнути.
   - *Clone URL*: `https://github.com/shevulkin/bofu.git`
     (якщо репозиторій приватний — спершу cPanel → SSH Access → створити ключ і
     додати його публічну частину в GitHub як Deploy key, а URL брати `git@`).
   - *Repository Path*: `/home/ВАШ_КОРИСТУВАЧ/repositories/bofu`

   **Не всередині `public_html`.** Клон містить теку `.git` — це вся історія
   проєкту, включно з тим, що колись із файлів видалили. У `public_html` вона
   стала б доступною з інтернету. Кореневий `.htaccess` таке звернення відбиває,
   але покладатись на це як на єдиний захист не варто: `.htaccess` не діє, якщо
   на хостингу обмежений `AllowOverride`.

2. **Перевірити, що гілка `main` вибрана** — розгортається HEAD саме тієї гілки,
   що зараз checked out.

3. Створити на сервері `config.local.php` (див. «Перенос на HostIQ», п. 4).
   Він **не в репозиторії** й розгортанням не переписується — у цьому й задум.

### Оновлення (щоразу)

1. Локально: `git push`.
2. cPanel → Git Version Control → **Manage** біля `bofu` → вкладка **Pull or Deploy**.
3. **Update from Remote** — забрати нові коміти з GitHub.
4. **Deploy HEAD Commit** — розкласти їх у `public_html/bofu`.
5. Відкрити сайт. Схема бази оновиться сама (`Schema::upgrade()` на першому ж запиті).

### Що робить `.cpanel.yml`

Копіює вміст репозиторію в `$HOME/public_html/bofu` через `rsync`, пропускаючи
`.git`, `.gitignore`, `tests/` і `docker-compose.yml`, і виставляє права на теки,
у які пише сам сайт.

Два рішення там варті пояснення, бо обидва — граблі, на які легко стати:

- **`rsync`, а не `cp -R *`.** Зірочка не бачить файлів, що починаються з крапки.
  У проєкті на них тримається все: кореневий `.htaccess` дає примусовий HTTPS і
  маршрутизацію через `index.php`, а `app/.htaccess`, `bin/.htaccess`,
  `storage/.htaccess`, `assets/uploads/.htaccess` закривають доступ до коду,
  логів і завантажених файлів. Розгортання зірочкою дало б сайт, який не
  маршрутизується і водночас віддає власний код. Документація cPanel окремо
  застерігає від зірочки — під неї потрапляє й `.git`.
- **Без `--delete`.** Він прибирав би з сервера файли, яких уже немає в
  репозиторії. Але поруч лежать завантажені фото товарів, яких у git не було
  ніколи, і помилка в одному рядку виключень коштувала б їх усіх. Стара копія
  файлу — проблема, яку видно й можна виправити; стерті фото — ні. Якщо колись
  знадобиться прибирати старі файли, робіть це руками у Диспетчері файлів.

### Якщо розгортання не спрацювало

- **«dirty working tree»** — у клоні на сервері хтось правив файли руками. cPanel
  відмовляється розгортати поверх правок, щоб їх не втратити. Або приберіть
  правки (Git Version Control покаже, які), або переносьте їх у репозиторій.
- **rsync not found** — рідко, але буває. Замініть у `.cpanel.yml` рядок rsync на
  `/bin/cp -R . $DEPLOYPATH/` (крапка, а не зірочка — вона бачить dot-файли),
  і додайте окремим рядком `/bin/rm -rf $DEPLOYPATH/.git`.
- **Файли лягли в `public_html/bofu/bofu`** — загубилась скісна риска в `./` або
  в `$DEPLOYPATH/`. Для rsync `./` означає «вміст цієї теки», а `.` — «цю теку».
- Сайт відкривається, але сторінки 404 — не доїхав кореневий `.htaccess`
  (та сама історія із зірочкою) або на хостингу вимкнений `AllowOverride`.
- **`File not found` на файл, який точно лежить на місці** — права на саму теку
  сайту. `public_html` належить користувачу, але групі `nobody`, і саме через
  групу до нього дістається веб-сервер; підтеки ж створюються з групою
  користувача. Якщо на теці сайту стоїть `0700` або `0750`, сервер не може в неї
  увійти — і повідомляє про це як про відсутній файл, хоча всередині все справне.
  Перевірити весь ланцюжок:
  ```bash
  ls -ld ~/public_html ~/public_html/bofu ~/public_html/bofu/index.php
  ```
  У теки сайту має бути `drwxr-xr-x`. Якщо ні:
  ```bash
  chmod 755 ~/public_html/bofu
  ```
  Звідки береться `0700`: `rsync -a` переносить права джерела, зокрема й на теку
  призначення, а клон, який cPanel створює в `repositories/`, має саме `0700`.
  Тому в `.cpanel.yml` `chmod` стоїть **після** rsync, а не до — інакше сайт лягав
  би рівно після кожного успішного розгортання, і виглядало б це так, ніби
  «деплой щось зламав».
- `$HOME` не розкрився — впишіть шлях повністю: `/home/ВАШ_КОРИСТУВАЧ/public_html/bofu`.
  Ім'я користувача видно у cPanel угорі праворуч і в шляхах Диспетчера файлів.

### Перед першим розгортанням у прод

Схема бази створиться сама, але **демо-дані з локальної бази переносити не можна**.
Сідер заводить трьох користувачів `@bofu.local` — один із них адміністратор, — а
також приклади товарів, категорій, магазинів і замовлень. На бойовому сайті це
означало б чужий адмінський обліковий запис і вітрину з вигаданим товаром.

Порядок для чистого старту:

1. На хостингу створити **порожню** базу й вписати її в `config.local.php`.
2. Відкрити сайт. `App::dbReady()` побачить порожню базу, створить таблиці й
   запустить сідер — тобто демо-дані зʼявляться знову, тепер уже на проді.
3. Увійти своєю поштою (кодом із листа або через Google), видати собі права
   `php bin/cli.php grant-admin ваша@пошта`, після чого **видалити демо-користувачів**
   в адмінці → Користувачі, а демо-товари, категорії та магазини замінити справжніми.

Якщо ж переносите локальну базу дампом (варіант із «Перенос на HostIQ», п. 1–2),
те саме прибирання зробіть **до** експорту або одразу після імпорту. Заразом
приберіть із `config.local.php` рядок `demo_login`, якщо він там лишився: функції вже
немає, а рядок збиває з пантелику.

## Карта точок продажу

Карта показується у двох місцях: при виборі самовивозу в оформленні та на сторінці
«Де нас знайти» (`/stores`). Обидва працюють і без неї — тоді покупець бачить адресу
з кнопкою «прокласти маршрут», і сторінки нічого не втрачають, крім самої карти.
Тому вмикати її можна коли завгодно, а не «перед запуском».

Google згадується рівно в одному файлі — `assets/js/map.js`. Зміна постачальника
карт (той самий OpenStreetMap, якщо не хочеться прив'язувати картку) коштує його
одного: решта — координати, поле в адмінці, сторінки — від постачальника не залежить.

### Що куди їде

| | Де живе | Їде з git |
|---|---|---|
| Код карти, сторінки, поля | файли | так |
| Стовпці `stores.lat` / `lng` | схема | так (створяться самі, п. 7 вище) |
| Ключ Google Maps | таблиця `settings` | **ні** — вписати в адмінці на сервері |
| Координати магазинів | таблиця `stores` | **ні** — заповнити в адмінці на сервері |

Ключ навмисно не у файлах: у git він не має опинитись ніколи. Якщо базу переносили
дампом (п. 1–2), то і ключ, і координати приїдуть разом із нею.

### Ключ

1. [Google Cloud Console](https://console.cloud.google.com/google/maps-apis/credentials) →
   проєкт із прив'язаним платіжним акаунтом (без картки ключ не видають навіть під
   безкоштовний обсяг).
2. Увімкнути **Maps JavaScript API** — саме його, не Embed і не Static.
3. Створити ключ і одразу обмежити:
   - *Application restrictions* → **Websites**, і **два рядки**:
     ```
     https://ваш-домен/*
     https://www.ваш-домен/*
     ```
     Обидва обов'язково: `https://bofu.ua/*` не покриває `www.bofu.ua` — для Google це
     різні реферери. Для розробки додайте ще `https://localhost/*`.
     Схема завжди `https://`: `.htaccess` примусово редіректить на HTTPS, тож інших
     реферерів не буде.
   - *API restrictions* → **Restrict key** → лише Maps JavaScript API.
4. Поставити **добову квоту** в консолі. Ключ їде у HTML кожної сторінки з картою —
   інакше Google Maps не працює. Обмеження за доменом плюс стеля квоти і є те, що
   робить нульовий рахунок гарантією, а не сподіванням: секретності тут не буває.
5. Вписати ключ: **Адмінка → Налаштування → «Google Maps: ключ»**.

Зміни в обмеженнях застосовуються не миттєво — до кількох хвилин.

### Координати магазинів

**Адмінка → Магазини**, поле «Координати». Три способи, усі три робочі:

- **📍 обрати на карті** — відкриється карта, клацнути по своєму входу, мітку можна
  перетягнути. Кнопка з'являється лише коли заданий ключ.
- Вставити пару чисел із Google Maps: права кнопка по місцю → перший рядок меню.
  Кома як десятковий знак (`50,4501, 30,5234`) теж підійде — саме так її копіює
  система з українською локаллю.
- Вставити посилання на місце — розберемо.

Поруч із заповненим полем є «перевірити →»: воно відкриває цю точку в Google Maps.
Натисніть після заповнення — пара чисел виглядає правдоподібно й тоді, коли вказує
на сусідній квартал, і оком це ловиться лише на самій карті.

Точка без координат лишається в списку самовивозу, але не має мітки на карті.
Пошуку адреси у вікні вибору немає навмисно: він живе в окремому API Google (Places)
з окремою оплатою, тобто коштував би грошей при кожному відкритті — заради дії, яку
роблять раз на магазин.

### Якщо карта не з'явилась

F12 → Console. Google називає причину прямо:

| Помилка | Що робити |
|---|---|
| `RefererNotAllowedMapError` | домен не доданий у ключ, або зміни ще не поширились |
| `ApiNotActivatedMapError` | не увімкнено Maps JavaScript API |
| `BillingNotEnabledMapError` | не прив'язано платіжний акаунт |
| `InvalidKeyMapError` | ключ скопійований з помилкою |

Якщо помилок немає, а карти теж — перевірте, чи є хоч в одного **активного** магазину
координати: без них блок карти не виводиться зовсім.
